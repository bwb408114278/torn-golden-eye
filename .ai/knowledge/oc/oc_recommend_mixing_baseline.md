### 2.2 已明确的目标口径（用户定义，优先级最高）

1. 推荐的目的**不是分钱，是让帮派赚更多的钱**。
2. **有效工时才叫帮派产出**。个人和帮派的一切收益都来源于有效工时：出工才有钱，摸鱼没有。
3. 大锅饭里**等级（rank）不参与分钱**，这是对「分配方式」的共识决策，不是遗留缺陷。
4. 高系数岗位在设计上就是「高权重 + 高 best_success」的岗位，应让能力强的人去。
5. 「时间」是第一因素，「能力」是第二因素。
6. **停转**与**空转**是两个必须进入模型的事实基础。
7. 一个人一个月理论上可接约 30 个队 → 资源单位是**人天**，不是「队数」。
8. 只按**当前快照**评估，不做「等下一次刷新」的期权定价；空转期间鼓励换队。
9. 工分**不需要**对真实空转时长敏感，保持序数阶梯即可。
10. **收益经验规则：高级比低级多，人多比人少多。**（v1.1 新增，已实测验证见 C-G1 / C-G2）
11. 只处理**大锅饭**口径的收益计算；非池化（无大锅饭）的收益方式不实现、也不需要实现，但语义上要能区分。
12. 每轮结论必须写回本文档。

### 2.3 关于本方案思路的一句话总结（用户确认）

> 用户的总结：「归一化后统一计算」。

**确认正确**，但需补充精度：归一化包含两层，缺一层就不成立。

| 层 | 内容 | 作用 |
|---|---|---|
| **量纲归一** | 一切折算到 `净产出 / 实际占用人天` | 让不同等级、不同人数、有池/无池、链式/单步都能同尺度比较 |
| **数据源归一** | 名单内用实测 UPH；名单外用「等级 + 人数」映射实测值，并按链补前置人天 | 让「没有历史收入的 OC」也能进入同一个排序 |

归一化**只用于推荐排序（帮派口径）**，不改变分钱规则（个人口径）。分钱仍由工分 × 系数决定，二者严格分离（C-F3）。

## 3. 事实基线（代码级确认）

### 3.1 收益分配方式的准确命名（术语纪律）

> **禁令：不要把 `EQUAL` 叫「均分」或「平分」。** 历史上确实存在过**完全平均分（人头均分）**的模式，与 `EQUAL` 不是一回事。代码与数据库里的枚举名 `EQUAL` 只是历史命名残留。

| 分配方式 | 计算口径 | 是否池化 | 现行系统 |
|---|---|---|---|
| **完全平均分（人头均分）** | 池子 ÷ 参与人数，与工时无关 | 池化 | **历史上存在，现已不存在；不实现、不处理** |
| **有效天数分配（系数恒为 1）** | 有效工时 = 工分 × 1 = 工分 = 天数，按天数占比分 | 有池化（大锅饭）与非池化两种 | 本系统**只处理大锅饭口径** |
| **系数加权分配** | 有效工时 = 工分 × 系数，按有效工时占比分 | 池化（大锅饭） | 现行 |

关键点：**系数为 1 时，有效工时 = 天数**，因此「有效天数分配」与「工分模式」是同一件事，不是两种模式。用户口径：*"我之前说的有效天数分配方式其实跟你说的工分模式是一种"*。

补充：

- **范围**：由 `torn_setting_oc_reassign_oc`（帮派维度名单）决定；名单外的 OC 不进入池子。
- **结算周期**：按自然月，按「结算叶子完成月份」归属（跨月链整条归入叶子月份）。
- 代码依据：`TornOcWorkingHourService#calculateWorkingHours` L60-63，`EQUAL` 时 `coefficient = BigDecimal.ONE`。

### 3.2 工分（baseWorkingHours）—— 固定名义阶梯

**定义：工分 = OC 人数 − 已加入人数（含自己）**

**关键性质：工分只由「加入顺序」决定，是固定名义阶梯，与真实的空转/停转时长无关。**

代码依据：`TornOcWorkingHourService#calculateWorkingHours` L53-57

```java
int totalSlots = slots.size();              // 按 joinTime 升序
for (int i = 0; i < slots.size(); i++) {
    int baseWorkingHours = totalSlots - i;  // 第 1 个加入 = N，最后一个 = 1
}
```

4 人 OC 示例：

| 加入顺序下标 i | 已加入人数 | 工分 |
|---|---|---|
| 0（第 1 个加入） | 1 | 4 |
| 1 | 2 | 3 |
| 2 | 3 | 2 |
| 3（第 4 个加入） | 4 | 1 |

**推论（置信度高）**：在标准节奏（每 24h 进 1 人）下，第 i 个加入者恰好要等 `24h × 工分` 才执行，因此该阶梯使得「每个位置的单位时间收益相同」。这是分配公平性的实现方式，也是「工分不需要对空转时长敏感」的根本原因。

**边界**：若队伍不是按 24h 节奏补人（瞬间补满、或停转后连补两人），工分与实际等待不再成比例，先/后加入者的单位时间收益会出现差异。这是设计上接受的近似，不修正。

### 3.3 有效工时

**有效工时 = 工分 × 系数**

- 系数为 1 时，**有效工时 = 工分 = 天数**（这就是「有效天数分配」）
- 系数来源：`torn_setting_oc_coefficient`，键为 `(faction_id, oc_name, rank, slot_code)`，按 `pass_rate_min < passRate <= pass_rate_max` 取 `coefficient`
- 查不到时 `TornSettingOcCoefficientManager#getCoefficient` **静默返回 `BigDecimal.ZERO`**（缺陷，见 5.8 D6）

### 3.4 个人分钱公式

真正的个人分配发生在**月度汇总**：`TornOcIncomeService#calcMonthlyIncomeSummary` L202-233

```text
月总奖励   = Σ(本月成功结算叶子的总奖励)      // 按叶子去重，同叶子奖励不一致直接抛异常
月总成本   = Σ(本月全部明细行的 item_cost)
月净收益   = 月总奖励 − 月总成本
个人占比   = 个人本月有效工时 / 全月总有效工时
个人净收益 = 月净收益 × 个人占比
个人最终收益 = 个人净收益 + 个人道具成本（全额报销）
```

> **⚠ 重要陷阱**：`torn_faction_oc_income.final_income` **不是个人份额**，而是**整条链的净收益快照**，同一链上每一行都相同。
> 代码依据：`TornFactionOcIncomeDO` L109 `this.finalIncome = income.getNetReward()`。
> 实测证据：帮派 2095 的 `Clinical Precision`（rank 8，4 人，oc_id 2325746）四行 `final_income` 全为 `69,435,303`，而四人的 `effective_working_hours` 分别为 59.2 / 37.2 / 30.0 / 20.8。
> **任何直接拿该列做逐人收益分析的结论都是错的。**

### 3.5 停转

```text
R1 = T1 + 24h
Rn = max(Tn, Rn-1) + 24h
```

- `Tn <= Rn-1`：加入不产生延迟
- `Tn > Rn-1`：**已停转**，从实际加入时刻起 `+24h`，全队顺延

### 3.6 空转

**定义（用户口径）**：每个 slot 的进度要在上一阶段 turn over（`R_prev`）之后才开始累积；在此之前加入的人进度恒为 0。这段「已经入场但进度不走」的等待就是空转。全队必须**依次**推进到 100% 才执行。

**空转不进入工分**（工分固定），只影响三个真实量：

1. **实际占用人天** = `executed_time − join_time` → 帮派的真实资源消耗
2. **个人收益 / 人天** = `工分×系数 / 实际占用天数` → 分母变大则单位时间收益被稀释
3. **全队完成时点** → 推迟即风险（被抢、失败、人力锁死）

### 3.7 三个口径必须严格分开

| 口径 | 用途 | 单位 | 来源 |
|---|---|---|---|
| 工分 / 有效工时 | 分钱（账面） | 工分、有效工时 | `base_working_hours` / `effective_working_hours` |
| 实际占用人天 | 帮派资源预算（真实） | 人天 | `executed_time − join_time` |
| 净产出 | 帮派产出（推荐排序用） | ISK | `reward_money + Σreward_items_value − item_cost` |

**跨收益模式比较必须用「工分」或「人天」，不能用「有效工时」**：系数加权模式系数均值约 13~16，与系数=1 模式不同量纲，直接用有效工时比较会得出完全相反的结论（见 4.2）。

### 3.8 链式 OC（v1.1 新增）

部分 OC 有前置步骤（`previous_oc_id`），形成链：

- `No Reserve`(r5) → `Bidding War`(r6)
- `Lock Stock`(r8) → `Hostile Takeover`(r9)
- `Stacking the Deck`(r8) → `Ace in the Hole`(r9)
- `Manifest Cruelty`(r8) → `Gone Fission`(r9) → `Crane Reaction`(r10)

**关键事实（实测，见 C-H1）**：**链上的前置步骤奖励恒为 0**（`reward_money` 与 `reward_items_value` 全空）。收益只在叶子节点结算。

因此：**链的真实产出 = 叶子奖励；链的真实成本 = 整条链的人天之和**。比较时不能按单步 OC 独立计算。

补充（Q8 实测确认）：**即使前置步骤成功，只要叶子失败，整条链的收益仍为 0。** 因此链的期望产出必须按「全部尝试（含失败与半途而废）」的人天摊销，不能用成功样本的人天。

### 4.12 Q5 专项：会不会把高能力选手排到低级 OC（v1.4 新增）

**（1）能力 × 等级的实际分布**（2026-08 起，按成员平均成功率分档统计加入次数）

| 能力档 | rank 1–6 次数 | rank 7–10 次数 | 低级占比 |
|---|---|---|---|
| A：≥85% | 217 | 954 | **18.5%** |
| B：75~85% | 1,011 | 6,027 | 14.4% |
| C：65~75% | 981 | 3,364 | 22.6% |
| D：<65% | 915 | 304 | **75.1%** |

分布确实是分层的：高手 81.5% 集中在高等级，低手 75.1% 集中在低等级。

**（2）错配的成本算式**

若选手最终一定会接到一个高级 OC，那么"先做一个低级 OC"与"干等"相比：

```text
方案 A（干等 T 天，然后做高级 OC）：耗时 T + 4.5，收益 X_high
方案 B（先做低级 OC 4 天，再高级）：耗时 4 + 4.5，收益 X_low + X_high
B 优于 A  ⇔  T > 4
```

**即：只有当"等下一个高级 OC"的时间超过低级 OC 的占用天数（≈4 天）时，做低级 OC 才划算。** 否则它只是把高级 OC 往后推 4 天，白占人力。

**（3）代入实测**

- 高手（≥85%）的等待间隔：P50 0.05 天、P90 0.84 天、**≥4 天仅 2.1%**
- 头部帮派利用率 87~94%，成员背靠背接单

**结论：对高能力选手，约 97.9% 的场合做低级 OC 是净亏；截断（不推非大锅饭 OC）在"保护高手"这个目标上基本正确、成本极低。** 真正会错配的只有那 2.1% 的长间隔场景。

**（4）因此正确规则是"条件推荐"，不是"一刀切截断"**

```text
推低级 OC 的充分条件：
  该成员已闲置时长 + 预计等待时长  >  低级 OC 的预计占用天数（≈4 天）
```

按当前数据该条件只在约 2% 的场合成立；而低能力成员（<65%）本来就有 75% 的参与在低等级，属于正常出口，不是错配。

## 5. 已闭环结论

### 5.1 准入层（对应 P1）

**C-A1｜P1 的根因不在评分，在准入过滤。**
收入层使用 `getRotationOcNames`（大锅饭名单）是**正当的**：池子本来就只算名单内的 OC。但推荐层**复用了同一个名单**，导致名单外的 OC 永远进不了候选池。三处越界调用：

- `TornOcRecommendService#shouldSkipOc` L164
- `TornOcAssignService#allocateGlobally` L189
- `TornOcRecommendManager#checkIsReassignRecommended` L121

**C-A2｜准入判据应从「在不在名单」改为「能不能估出单位人天产出」。**
数据条件已具备：`torn_faction_oc.reward_money` + `reward_items_value` 对**全部** OC 都有记录（名单内外一致），只有 `torn_faction_oc_income` 才只覆盖名单内。

**C-A3｜「新队/停转」不该靠特判置顶，应靠统一度量自然冒头。**
只要度量里有「实际占用天数」作分母，停转补位的占用天数最短，排序自然靠前。

**C-A4｜「纯道具奖励的 OC」是准入层的第二个坑。**
`Ship Happens` 的 `reward_money = 0`、奖励全在 `reward_items_value`（176.7M）；`Window of Opportunity` 同理（84.8M）。任何只用 `reward_money` 或 `expected_reward` 估算产出的路径，都会把它们判为 0 产出 → 永不推荐。
**正确口径：奖励 = `reward_money + Σ(按 # 拆分 reward_items_value)`**（`TornOcIncomeService` L117-119 已是此口径）。

### 5.2 混算层（对应 P3）

**C-B1｜统一度量 = 帮派净产出 / 实际占用人天。**

- 名单内 OC：用 `torn_faction_oc_income` 的实测口径（已含道具成本与失败损失，且链条已按链聚合）
- 名单外 OC：`(reward_money + Σitems) × P(成功) − 预期道具成本` 除以预期人天

**C-B2｜混算的核心困难不是「两套分数怎么加权」，而是「名单外 OC 没有 UPH 历史」。**
用 C-A2 + C-G 的经验映射补上后，两套分数退化为同一套公式，不需要加权融合。

**C-B3｜评分公式（现有 0.8/0.2 加权）不是瓶颈。**
瓶颈是候选池是否完整。候选池残缺时调权重，收益远小于补齐候选池。

**C-B4｜排序规则：等级降序，其次人数降序（字典序，不可相乘）。**
实测 6 个 OC 全部一致（4.7）。机制：奖励随等级与人数**超线性**增长，而人天基本线性增长（人天 ≈ 人数 × 4.5 天），故 M/人天 随两者同时上升。

**C-B5｜「人数」不是可调变量。**
人数是 OC 的固有属性，所以该规则只用于**跨 OC 排序**，不构成优化杠杆。

**C-B6｜必须按「链」聚合，不能按单步 OC 比较。**
前置步骤奖励为 0 却消耗人天。按单步比较会把 rank 9/10 高估一倍以上（Hostile Takeover 单步 28.31 vs 链级 16.50）。

**C-B7｜名单内链条的实测 UPH 天然已扣前置成本。**
`generateAndSaveIncome` 会把整条链每个步骤的有效工时都计入月度分母，而收入只取叶子 → 前置成本自动被摊掉。**名单外估算必须自己补前置人天，否则高估。**

### 5.3 有效天数分配层（原「均分层」，对应 P4）

**C-C1｜「有效天数分配如何混入评分」是伪问题。**
帮派产出 = 池内所有 OC 的总产出，**与怎么分钱无关**。因此系数=1 / 系数加权不应影响帮派口径的排序结果。

**C-C2｜实测支持上述判断。**
按工分归一后，系数=1 帮派 14.215 / 7.768 / 7.473 M/工分，系数加权帮派 8.090 / 7.517 / 6.952 / 5.919 M/工分，**没有系统性优劣**（4.2）。

**C-C3｜系数=1 的分配是「按工分（天数）阶梯 4:3:2:1 分」，不是人头均分。**
实测：帮派 16335 的 `Clinical Precision` 4 人 OC，`base_working_hours` = 4/3/2/1，`effective_working_hours` = 4/3/2/1。**术语见 3.1，禁止叫「均分」。**

**C-C4｜系数=1 模式把激励职能转移给了推荐系统。**
该模式下强者去关键岗位不再有额外金钱回报，与「让能力强的人去重要岗位」冲突。**推荐侧用帮派口径排序，本来就会把强者推到高产出岗位**，相当于替系数补上激励。这是该模式下推荐系统的额外职责，不是缺陷。

**C-C5｜分钱模式只应进「个人收入展示」，不应进「帮派排序」。**

### 5.4 新手层（对应 P2）

**C-D1｜P2 的根因是候选池错误，不是评分问题。**
`TornOcRecommendService` L181-183 在 `matchedData == null` 时直接跳过；而成功率矩阵只从已占用 slot（`updateJoinedUserPassRate`）或按 key 拉取（`updateEmptyUserPassRate`）写入。新手矩阵覆盖不足 → 全部候选被判「无数据」→ 返回空。

**C-D2｜闲置者的机会成本为 0，任何正产出都应推荐。**
新手的替代方案是「继续摸鱼」（产出 0），因此 rank 1~2 的低产出队伍对他仍是**正增益**。低级队对「本来闲着的人」是正产出，对「本可以进高级队的人」才是负产出。规则应是**「不拦着能往上走的人」**。（v1.4 修订：需叠加 C-D4 的「等待成本 > 占用成本」条件，见 4.12）

**C-D3｜新手不需要大锅饭资格。**
候选池应是「所有他的人员成功率下限达标的空位」，按单位人天产出排序。

**C-D4｜低级 OC 的推荐条件是「等待成本 > 占用成本」，不是「有闲就推」。**
只有当"预计等待下一个高等级 OC 的时间 > 低级 OC 的占用天数（≈4 天）"时，做低级 OC 才划算；否则只是把高等级 OC 往后推（4.12）。实测该条件仅在约 2% 的场合成立。

**C-D5｜截断非大锅饭 OC 在"保护高手"上是对的，但不该成为准入硬闸。**
高手 81.5% 的参与已在高等级，且约 97.9% 的场合做低级 OC 净亏 → 一刀切截断对高手的损失很小；但它同时让「那 2% 的长间隔场景」和「新手首次入场」拿不到任何推荐。正确做法是**分层 + 条件推荐**。

**C-D6｜活跃成员几乎不闲置，P2 的危害是"推荐返回空"而不是"帮派丢人天"。**
头部帮派利用率 87~94%，成员间隔中位 1~2 小时。因此 P2 的实际问题在体验与准入逻辑，不在人天浪费（4.3 / 4.12）。

### 5.5 停转 / 空转（对应 P2 的事实基础）

**C-E1｜工分是固定的名义阶梯，与真实空转/停转无关。**（3.2）

**C-E2｜空转不进工分，只进人天成本、收益分母与完成风险。**（3.6）

**C-E3｜「停转置顶」的正确理由有两个，都不含「个人收益/天更高」。**
1. 帮派侧：停转队已有 N−1 人的时间被锁死，我补位后 24h 内全队释放 → **单位人天的边际增益最大**
2. 个人侧：占用天数最短，可立即接下一个队 → 灵活性最高

**C-E4｜停转的 OC 全部优先，但停转内部不是"无脑优先"。**（v1.5 修订，R22）
- **第一键**：是否停转（停转优先——占用最短、可立即释放全队）
- **第二键**：该 OC 的期望 M/人天（高手要先去更重要的位置；把他浪费在次要岗位上，对他自己的能力也是浪费）
- **第三键**：剩余空位数（越少越接近开动。这是**后置条件**，用户明确）

原「停转只指向最后一个空位」的说法已被推翻（R22）：多个停转并存时，空位数不是首要判据。

**C-E7｜被锁死人天只统计 progress > 0 的成员。**（v2.3 新增，2026-10-23）
空转成员（progress = 0）可自由换队不损失进度；有进度成员（progress > 0）被锁死在当前 OC，只能本队换岗。因此被锁死人天的范围是「已加入且 progress > 0 的成员」，不含空转成员。这是空转与停转的根本区别：空转鼓励换队，停转必须优先补位。

**C-E5｜「空转时鼓励换队」有量化依据。**
空转拉长实际占用天数而工分固定 → 个人单位时间收益被稀释。

**C-E6｜「新队/停转加入很赚钱」的真因是「本来闲着」。**
各位置的单位时间收益被工分阶梯拉平（3.2 推论），真正的收益来源是「从 0 变成有」。

### 5.6 定价与激励

**C-F1｜priority 与 best_success 各据一层，不是竞争关系。**

```text
期望收益 = P(成功) × E[奖励 | 成功] × 队伍价值
             ↑              ↑
        priority 在这   best_success 在这
```

**C-F2｜priority 从不进入分钱公式。**
分钱只认 `coefficient`。priority 只影响 P(成功)。

**C-F3｜系数表是分钱基准，推荐算法是另一套，二者不得互相取代。**
ΔP 属推荐侧概念且非必须；它不能替代也不能修改系数表。

**C-F4｜不设「整队成功率下限」。**
已有「人员成功率下限」（`checkpoint_pass_rate`）。数据支持：短板 `min` 的 r 仅 0.1229，同均值区间内无增量信息（4.5）。

### 5.7 术语、排序规则与链式口径（v1.1 新增）

**C-I1｜`EQUAL` ≠ 均分。** 正确叫法：「系数恒为 1 模式」/「有效天数分配」。真正的完全平均分（人头均分）历史上存在过，现已不存在，本系统不处理也不需要处理。（3.1）

**C-I2｜系数为 1 时，有效工时 = 工分 = 天数。** 因此「有效天数分配」与「工分模式」是同一件事。（3.3）

**C-I3｜「有效天数分配」也有池化与非池化之分；本系统只实现大锅饭（池化）口径。**

**C-I4｜统计口径三条纪律。**
1. 平均奖励**只统计成功样本**（失败计 0 会污染等级间比较）
2. 奖励必须**现金 + 道具**两部分（4.10 的 Ship Happens / Window of Opportunity 是纯道具）
3. 链式 OC **必须按链聚合**（4.8）

**C-G1｜「高级比低级多，人多比人少多」已被实测验证。**
按 `(rank desc, slots desc)` 排出的顺序 = 按 M/人天 排出的顺序，6 个 OC 全部一致（4.7）。

**C-G2｜该规则是字典序，不是相乘。**
反例验证：Clinical Precision(r8,4人) M/人天 8.05 > Cleared for Takeoff(r7,6人) 6.94；若按「rank × 人数」相乘（8×4=32 < 7×6=42）会排反。

**C-H1｜链上前置步骤奖励恒为 0。**
实测 168 条链，前置的 `reward_money` 与 `reward_items_value` 全为空/0。

**C-H2｜链的真实产出 = 叶子奖励；链的真实成本 = 整链人天之和。**

**C-H3｜只为叶子记奖励不是缺陷。**
`generateAndSaveIncome` 的 `totalReward` 只取叶子，与「前置零奖励」的事实一致。

**C-H4｜链只在叶子成功时结算。**（Q8 闭环）
前置步骤无论成功与否都拿不到钱；**叶子失败则整条链 0 收益**。实测：`Gone Fission` 的 7 次成功全部贡献 0，因为其下游 `Crane Reaction` 失败。

**C-H5｜链必须用「期望口径」比较，不能用「成功条件」口径。**（R19）
3 步链转化率 20%，期望 7.44，低于单步 Break the Bank 的 8.84；而成功条件口径会把它错排到第一（22.08）。

**C-H6｜「高等级 ≠ 高期望」的第一个反例是 r10。**
单次奖励 1,333M（全部 OC 中最高），但期望 M/人天 7.44（第 4）。原因是多级串联的转化率衰减。

**C-H7｜新增指标：转化率（根实例 → 收到钱的叶子）。**
它是链式 OC 排序的关键中间量：2 步链 55~61%，3 步链 20%。只看奖励规模会严重高估多步链。

**C-H8｜即使按最高收益，r10 链仍不敌 r9 双步链。**
1.65B 口径下 r10 期望 9.20，低于 r9 链 A 的 14.27、链 B 的 11.92，也低于 Break the Bank 的 11.24。盈亏平衡需 1.83B~2.56B，超出上限 11%~55%。（4.11）

**C-H9｜r10 的 20% 转化率样本量不足，不能当稳定先验。**
15 次起手、3 次收到钱，Wilson 95% 置信区间约 **[7.0%, 45.2%]**；且高度依赖帮派（PN 2/8、BSU 1/1、CCRC 0/1、SVH 0/3、PTA 0/2）。任何基于 20% 的结论都应标注为弱证据。
对比：链 A 60.9%（95%CI 46.5%~73.6%）、链 B 55.7%（95%CI 45.8%~65.2%），证据强度明显更高。

**C-H10｜r10 实测样本来自 5 个帮派，但只有 BSU 把它纳入了大锅饭。**
PN（PHN）跑过 2 次成功（各 1.5B）但名单里没有 Manifest Cruelty / Gone Fission / Crane Reaction → 属**非池化收益**，本系统不处理（见 2.2 第 11 条）。因此"r10 值不值得"在单个帮派里首先是**要不要入池**的运营决策，不是推荐算法能决定的。
用户补充：PN 与 NOV 均未开放 r10 大锅饭；BSU 曾把成功率全部设为 0 做实验；目前没有帮派愿意用真金白银长期尝试，成员能力也不足以稳定盈利。

### 5.9 推荐评分与排序键（v2.4 定稿，取代 v1.6 机会成本口径）

```text
推荐评分 = 单位人天产出 V × 开动紧迫度 f

V = 该 OC / 链的期望净产出 ÷ 期望总人天          // 度量层输出（6.1），等级越高越大
f = 旧时间曲线 ÷ 100                            // 0.10 ~ 1.00
    已停转 1.00 · 新队 0.95 · 6 小时内 0.95~1.00 · 24 小时 0.65
    48 小时 0.35 · 72 小时 0.20 · 72 小时以上 0.10~0.20
```

排序：评分降序 → 单位人天产出降序 → 期望人天升序 → 剩余空位数升序 → ocId / slotId 升序（D4）。

**C-M1｜评分恒非负，永远不做「负分不推荐」。**（用户 2026-10-25）
两个因子都是非负量，评分不可能为负；因此不存在「明明还有空位，却告诉用户没有合适加入的 OC」。
只有真的不存在任何可填空位时，推荐结果才为空。

**C-M2｜时间权重由开动紧迫度直接承担，不再靠人造权重。**（用户 2026-10-25）
全帮产能 ≈ Σ(各队单位人天产出 × 可用人天)，一个 OC 完成即释放 4~6 人，越早开动越早回收人力。
停转队 f=1.00、55 小时队 f=0.31，相差三倍以上；旧版「时间占 80%」想表达的就是这件事，
现在由量纲本身表达，不再需要给时间/等级人为分配权重。

**C-M3｜替代概率不参与评分。**（用户 2026-10-25，图1/图3）
本帮派实测（20465，2026-10-25 快照）rank 1~9 每个岗位的可填人数均值 25.8~79.8，最小值只有 rank 10 出现过 1 人；
而空位数只有 1~6，于是 `人数 / 空位数` 恒被截到 1，`期望收益 × (1 − p)` 恒为 0，
等级与收益被整体抹掉、排序退化成「别人等了多久 − 常量」。
替代概率保留为稀缺度分档（4.13 / C-J1 的实测结论仍有效），只用于解释展示。

**C-M4｜被锁死人天不进评分。**（用户 2026-10-25）
「别人已经等了多久」是沉没时间：它随时间自己变大、不封顶，且与等级无关，
曾导致「等得久的低等级队压过马上开动的高等级队，高手被塞进 4 级 OC」。
需要表达释放收益时改用稳定量（剩余空位 × 24h），并在「全帮流转」专题（Q17）中统一建模。

**C-M5｜推荐理由必须写明排序依据。**（用户 2026-10-25：先按「写明」做，不加硬准入）
每行给出两段：还要等多久（停转倒计时 / 已停转 / 新队）、成功率档位（超高 / 高 / 达标）。
**经济性不写进理由**（v2.5 修订）：金额是估计值，写进文案只会被当成账本；经济性统一由百分制评分徽章承载（C-M9）。
用户据此仍能解释「为什么推这支队」，也能解释「为什么高手会先补一支马上开动的低等级队」。

#### 5.9.2 人天、样本与展示口径（v2.5 定稿，回答「用钱排序合适吗 / 金额准不准」）

```text
期望人天 = 6.0 天/岗位 × 团队人数
团队人数 = 目录配置 required_members > 该队实际岗位数(torn_faction_oc_slot) > 1
实测与映射 = 实测 × n/(n+10) + 等级映射 × 10/(n+10)        // n = 该OC历史尝试次数
对外评分 = 100 × ln(1 + 评分/0.5M) ÷ ln(1 + 12M/0.5M)      // 1 ~ 100 的百分制
```

**C-M6｜单岗位人天取实测 6.0 天，不再用 4.5。**（2026-10-25 实测）
ready_time − create_time 的实际占用中位数：3 级 6.56、4 级 5.57、5 级 5.00、6 级 5.78、7 级 6.02、8 级 5.69、9 级 6.02、10 级 6.53，合计取 6.0。旧值 4.5 把每支队的人天低估约 25%，进而把单位人天产出整体高估同样比例；统一常量只做整体缩放，不改变同一紧迫度下的排序，因此跨等级差异（3 级比 8 级慢约 21%）留作后续精度项，不按等级分叉以免过拟合。

**C-M7｜配置缺岗位人数时，必须用该队实际岗位数兜底。**（2026-10-25，图3 的残留根因）
`torn_setting_oc` 的 `required_members` 在 1~6 级上整体缺失（配置只做到 7 级往上），旧实现按 max(1, 0)=1 处理，于是 4~6 人队的人天被低估 3~6 倍、单位人天产出被高估同样倍数。实测：Snow Blind r4（4 岗）虚高 4.0 倍、Leave No Trace r6（3 岗）虚高 3.0 倍；活跃队中 26 支队踩此坑。这是「高手被塞进 4 级」除时间权重之外的第二个根因。

**C-M8｜实测与等级映射按样本量加权，不设硬门槛。**（2026-10-25）
旧口径「成功 ≥3 次即纯实测」有两个毛病：① 6 次成功的样本标准误约 ±28%（二项分布、失败记 0 收益），会被顶到池子最前面（Lock Stock r8 ±28%、Hostile Takeover r9 ±25%、Ship Happens r8 ±17%）；② 恰好差一次样本的 OC 整段退回等级阶梯，而阶梯对个别 OC 偏差可达 −37%~+39%，比带噪声的实测更离谱。改为伪尝试 10 次的加权：509 次尝试约 98% 取实测，11 次尝试约 52% 取实测。主力队实测误差在 ±3%~±9%（Break the Bank 337 次、Blast 509 次、Clinical Precision 352 次）。

**C-M9｜对外只展示百分制评分，不展示金额。**（用户 2026-10-25 明确）
货币量纲只做排序内核：它的作用是相对比较，误差会被排名吸收；一旦展示成「3.72M/人天」，就会被当成账本，任何估算误差都变成对公式的质疑。对外换算为 1~100 的固定锚点百分制（0.5M 折 1 分、12M 折 100 分，对数刻度），与排序键严格单调，不会出现「评分高但排后面」。对数刻度而非线性，是因为 OC 产出跨等级差异极大（7 级约 2~3M/人天、9 级约 14M/人天），线性会让绝大多数真实推荐挤在个位数，或让 9 级队一律饱和。固定锚点保证同一支队在任何一次推荐里得分一致。

#### 5.9.1 历史口径（v1.6 机会成本，已于 v2.4 撤销，见第 6 章 R27）

推荐某个空位给某成员时，按以下顺序比较：

**v1.6 修正：用一个统一的量——「我不填这个位，帮派损失多少」（机会成本）——来排序。**
v1.5 的「停转 → M/人天 → 剩余空位数」三段式已被它吸收并取代（R23）。

```text
机会成本(不填) = 该 OC/链的期望收益 × (1 − 替代概率)
              + 被锁死人天 × 每日等待成本

其中：
  替代概率   = 除我之外还能填这个岗位的人数 / 岗位需求
              （= 0 时，我不填 → 该 OC 直接归零）
  被锁死人天 = 停转队里其他成员 × 剩余等待天数
```

推荐时按 **机会成本降序** 排列。这个单一量自动涵盖：

| 场景 | 机会成本 | 自然结果 |
|---|---|---|
| 我是唯一能填的 rank 9/10 关键岗位 | 极高（该 OC 归零） | 最高优先 ✅ |
| 停转队且我是最后一人 | 高（N 人天立即释放） | 次高 ✅ |
| 停转队但还有多个空位 | 中（只锁我自己） | 居中 ✅ |
| 大众 rank 7 岗位（37 人能填） | 低（别人 1 小时内补上） | 最低 ✅ |

**确定性 tie-break**：ocId / slotId 升序，保证结果可复现（D4）。

**C-J1｜岗位的可替代性差异极大，必须进入模型。**（4.13）
rank 7 岗位平均 66.2 人可填，rank 9 只有 4.6 人，rank 10 只有 2.5 人。2095 的 Ace in the Hole 关键岗位仅 1 人可填，而 Window of Opportunity 的 Muscle#1 有 37 人可填。

**C-J2｜「释放人的数量」不等于「补上缺口的能力」。**（R23）
被释放出来的成员大概率达不到 rank 9/10 关键岗位的要求；而其他 OC 里的人又被锁死，无法过来。所以填一个人的价值，取决于**这个位在他缺席时能不能被别人补上**，不是取决于填完后释放多少人。

**C-J3｜大量高等级岗位现在就是「0 人可填」的死位。**
rank 9 有 45/112 个岗位、rank 10 有 19/35 个岗位当前没有任何已测成员达标。这说明链 A / 链 B 的转化率损失（46→36→28、97→75→54）里，有一部分不是「不想做」，而是「没人能做」。

**C-J4｜排序用一个统一的量：机会成本。**
停转优先、高手去关键岗位、剩余空位少优先，三者在机会成本口径下自动成立，不需要三套规则（5.9）。

**准入条件（不是排序键）**

1. 该岗位的**人员成功率下限**（`checkpoint_pass_rate`）达标 —— P0 阶段用现有配置表达"能力分层"，不新造阈值（Q14）
2. 低级 OC 仅在 C-D4 的不等式成立时进入候选（Q13）

**Q13 的两个「等待」必须区分**

| 名称 | 含义 | 可算性 |
|---|---|---|
| **OC 内空转** | 我加入后到该 OC 执行之间的等待 | **可直接算**：停转队 = 24h；未停转 = 已排队时间 + 剩余轮次 × 24h |
| **市场等待 T** | 我**不接**这个低级 OC，要等多久才出现更高价值的可进空位 | 需估，无法从当前快照直接得出 |

C-D4 的不等式：

```text
接低级 OC 更优  ⇔  市场等待 T  >  低级 OC 的锁定时长
锁定时长 = 我的空转 + 该 OC 剩余执行时间      ← 可直接算
```

**T 的估法（按优先级）**

1. 该成员历史「上一单执行 → 下一单加入」间隔的 **P90**（实测：≥85% 档 0.84 天、<65% 档 1.26 天）
2. 该成员**无历史（新手）** → 退化为「当前快照里是否存在他能进且 M/人天 更高的空位」：**没有就推**
3. 帮派层面「每天新增 r7+ 空位 ÷ 可竞争成员数」作供给率参考

**代入现数据的效果**：高手 T(P90)=0.84 天 ≪ 锁定时长 ~4 天 → **永不触发低级 OC 推荐**；新手无历史 → 走第 2 条，**没有更好空位就推**。**这正好把 P2 解开，同时保持对高手的截断。**

**Q14 分两阶段定案**

- **P0（无 DAG）**：不新增阈值。能力分层 = 岗位自带的 `checkpoint_pass_rate` + 系数表分档，用现有配置表达。
- **P2（有 DAG）**：改用 **Δ期望收益**（填这个位对整队期望收益的增量）替代门槛表达。

**明确不做的事**

- 不按「是否在大锅饭名单」过滤（C-A1）
- 不设整队成功率下限（C-F4）
- 不设"等下一次刷新"的期权价值（目标口径 8）

### 5.10 准入率与稀缺度的口径（v1.7 新增，对应 Q16）

**C-K1｜准入率不需要做统计平滑。**（用户 2026-10-22 / 4.14）
三条理由合起来让「平滑」失去意义：① 门槛本身是配置（`torn_setting_oc_slot.pass_rate` 全局可调，rank 1–6 一律 60，rank 7–9 差异化到 62–69），不是物理常量；② 成员能力在涨，而系数表已经把「成功率 → 收益权重」做成连续映射（4.14.3）；③ 只有实力强到能开大锅饭的帮派才会遇到这个问题（4.14.1），样本偏差的方向是「能力充足」而不是「能力不足」。

**C-K2｜替代概率用当前快照直算，缺样本时取中性，不落成画像表。**
（v2.4 补充：替代概率**不再乘进推荐评分**——本帮派该值恒为 1，乘进去会把收益项整体归零（C-M3）；
它只作为「这个位有多少人能填」的稀缺度分档展示。）
这是 Q16 关闭后**唯一新增的实现约束**：

```text
替代概率 = count(除我之外、当前 pass_rate ≥ 该岗位门槛 的成员) / 该岗位需求人数

  有样本 → 直接用
  该岗位无人测过 / 门槛刚调过 → 视为「未知」，不做惩罚也不做奖励
                            → 让第二项（被锁死人天 × 等待成本）主导排序
```

**禁止**把替代概率缓存成「成员能力画像」之类的持久化派生数据：能力会涨、门槛会调，任何落库的画像第二天就过期，反而制造错误结论。每次推荐时实时算（已有 `torn_faction_oc_user` 与 `torn_setting_oc_slot` 两张表，成本可接受）。

**C-K3｜修正 4.13 的解读口径。**
4.13 测出的「rank 9 有 45/112、rank 10 有 19/35 个岗位 0 人可填」是 **2026-10 的快照，不是结构约束**。它**不构成**「高等级 OC 招不到人」的结论（R23 撤销时我把它说重了），也**不作为**推荐闸门或准入前置条件。它唯一的作用是代入 C-K2 算当前的替代概率。

**C-K4｜能力维度复用系数表，不另造分层。**
推荐侧要判断「这人够不够格 / 值不值得派去关键位」，直接读 `torn_setting_oc_slot.pass_rate`（够不够）与 `torn_setting_oc_coefficient`（值多少），与 Q14 的 P0 方案一致，与 C-G1（按「等级 + 人数」映射 M/人天）互补而不是重复。

**C-K5｜名单深度 = 能力前沿，但仍由人工维护 —— 这是 P1 的根因。**
名单分 5 层（6 → 8 → 9 → 11 → 13 个 OC，4.14.2），深度与帮派实力同向，说明**管理者本来就在按能力划前沿**；问题是这个前沿靠人手逐个帮派补，Ship Happens 补了 17 天（4.14.2）。因此 P1 的修法不变：**名单失效不得阻断推荐**，用映射值立即参与计算（C-A1 / Q7）。

**C-K6｜「名单深度自动推导」只是后续建议，不纳入本轮。**
既然前沿可以按「该帮派有多少人能过这个 OC 的岗位」推出来，长期可以让名单从配置项退化成派生视图。但这属于新能力建设，本轮不做（系统提示 9 / 10）。

### 5.11 候选池的粒度（v2.2 新增，对应 D3）

**C-L1｜同一 OC 的多个空位各自独立参与推荐，允许一个 OC 占满 Top-N。**（用户 2026-10-22）
多个成员会同时抢同一个岗位。抢位失败时，**同一 OC 的第二个岗位仍然值得加入**——如果推荐把同一 OC 去重成一行，用户就得重新请求一次指令才能看到同队的下一个位置。旧版「一个 OC 可能占满 3 个槽位」是**刻意设计**，不是缺陷。

**C-L2｜同队多岗位不是重复信息，而是备选梯度。**
同一 OC 内不同岗位的替代概率不同（稀缺岗位可填人数少），机会成本因此不同，排序天然把最不可替代的岗位排在最前。用户从上往下看就是一个「先抢最好、失败就退而求其次」的队列。

**C-L3｜剩余空位数继续作为同分决胜键。**
「缺人数少的 OC 更快凑齐开动」这一判断（C-E4 第三键）仍然成立，保留为机会成本之后的第四决胜键，不因「不去重」而失效。

-- 4.13 岗位稀缺度（按等级）
with req as (
  select s.oc_name, s.rank, s.slot_short_code, s.pass_rate
  from torn_setting_oc_slot s where s.deleted = 0
),
fa as (select distinct faction_id from torn_setting_oc_reassign_oc where deleted = 0),
x as (
  select fa.faction_id, req.rank,
         count(u.user_id) as known,
         count(u.user_id) filter (where u.pass_rate >= req.pass_rate) as eligible
  from req cross join fa
  left join torn_faction_oc_user u
         on u.faction_id = fa.faction_id and u.deleted = 0
        and u.oc_name = req.oc_name and u.rank = req.rank and u.position = req.slot_short_code
  group by fa.faction_id, req.oc_name, req.rank, req.slot_short_code, req.pass_rate
)
select rank, count(*) as slots,
       round(avg(known)::numeric,1) as avg_known, round(avg(eligible)::numeric,1) as avg_eligible,
       count(*) filter (where eligible = 0) as slots_with_0,
       count(*) filter (where eligible <= 1) as slots_with_le1
from x group by rank order by rank;

-- 4.7 单 OC 单位人天产出
with oc as (
  select o.id, o.name, o.rank,
         o.reward_money + coalesce((select sum(x::numeric)
             from unnest(string_to_array(nullif(o.reward_items_value,''),'#')) x),0) as reward
  from torn_faction_oc o where o.deleted = 0 and o.status = 'Successful'
), md as (
  select o.id, sum(extract(epoch from (o.executed_time - s.join_time))/86400.0) as member_days
  from torn_faction_oc o
  join torn_faction_oc_slot s on s.oc_id = o.id and s.deleted = 0
  where o.deleted = 0 and o.status = 'Successful'
  group by o.id
)
select oc.rank, oc.name, count(*) as n, avg(oc.reward) as reward,
       avg(md.member_days) as member_days_per_oc,
       avg(oc.reward)/nullif(avg(md.member_days),0) as reward_per_member_day
from oc join md on md.id = oc.id
group by oc.rank, oc.name order by oc.rank desc, reward_per_member_day desc;

-- 4.1 等级阶梯（成功口径 + 现金与道具）
select rank, count(*) as n,
       count(*) filter (where status='Successful') as n_ok,
       avg(case when status='Successful' then 1.0 else 0 end) as success_rate,
       avg(case when status='Successful' then reward_money end) as money_ok,
       avg(case when status='Successful'
             then coalesce((select sum(x::numeric)
                            from unnest(string_to_array(nullif(reward_items_value,''),'#')) x),0)
           end) as items_ok
from torn_faction_oc
where deleted = 0 and status in ('Successful','Failure')
  and executed_time >= '2026-09-01' and executed_time < '2026-11-01'
group by rank order by rank;

-- 4.2 按工分归一（按 oc_id 聚合，避免 total_reward 逐行重复计入）
with oc as (
  select faction_id, oc_id,
         max(case when is_success then total_reward else 0 end) as reward,
         sum(item_cost) as item_cost, sum(base_working_hours) as base_h
  from torn_faction_oc_income
  where deleted = 0 and oc_executed_time >= '2026-10-01' and oc_executed_time < '2026-11-01'
  group by faction_id, oc_id
)
select faction_id, count(*) as oc_cnt,
       sum(reward) - sum(item_cost) as net_reward, sum(base_h) as base_hours,
       (sum(reward) - sum(item_cost)) / nullif(sum(base_h), 0) as net_per_base_hour
from oc group by faction_id order by net_per_base_hour desc;
