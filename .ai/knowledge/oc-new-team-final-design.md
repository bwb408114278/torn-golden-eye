## 1. 产品定位

`OC新队` 是面向OC指挥官的**匿名刷新决策器**，不是成员排班器，也不能代替指挥官在游戏中执行刷新。

系统根据当前OC、成员能力、成员释放时间、准备阶段时间线和高阶后继义务，计算本轮可以安全执行的：

```text
(普通池刷新次数, 高阶池刷新次数)
```

命令只输出人工操作指令和当前现实OC占用摘要，不输出具体成员安排。

### 1.1 输出范围

允许输出：

- 快照时间；
- 普通池建议刷新次数；
- 高阶池建议刷新次数；
- 当前全部现实OC队伍数、已有人队伍数和无人队伍数；
- 当前实际占用的去重成员数；
- 满足任一计划内OC岗位实际门槛的达标成员数；
- 已占用达标成员数和空闲达标成员数；
- 是否只获得时间预算内的安全下界；
- 配置和求解警告。

禁止输出：

- 成员姓名；
- 具体岗位；
- 个人加入时间；
- 旧队补位动作；
- 人天；
- 高阶链运行状态；
- “安全并行20条”；
- 无限时间线吞吐量；
- 自动刷新成功等虚假表述。

### 1.2 人工操作边界

普通池和高阶池是两个独立的游戏内人工入口，均可连续刷新多次。

`TornFactionOcRefreshManager.refreshOc(version, factionId)` 仅同步Torn API数据，其中第一个参数是数据版本，不是游戏刷新次数。

## 2. 规划范围与容量口径

规划范围必须同时满足：

```text
帮派OC规划已启用
+ profile.plan_status = READY
+ Catalog配置校验通过
```

### 2.1 计划内OC

- 计划内无人OC：占用规划容量，数量大于0时展示；
- 计划内有人OC：已有成员和岗位固定，只证明剩余岗位及后继义务；
- 计划内高阶根：必须同时预留完整后继链。

### 2.2 非计划OC

- 非计划无人OC：不占成员容量，不展示；
- 非计划有人OC：不自动补位、不展示，但保留现实成员占用直到释放。

容量由“是否进入计划”决定，不由“是否无人”决定。

### 2.3 优先级

求解顺序固定为：

```text
现有计划内普通OC
→ 现有计划内高阶根及全部后继义务
→ 本轮新增普通池随机结果
→ 本轮新增高阶池随机结果
```

任何新增刷新建议都必须建立在现有计划义务已经可完成的基础时间线上。

## 3. readyTime与停转规则

`readyTime` 表示当前累计准备阶段结束、可以进入下一阶段的时间，不是整队完成时间。

### 3.1 递推规则

无人加入时：

```text
readyTime = null
```

第一位成员在 `T1` 加入：

```text
R1 = T1 + 24小时
```

后续成员在 `Tn` 加入，当前 `readyTime = Rn-1`：

```text
Rn = max(Tn, Rn-1) + 24小时
```

- `Tn <= Rn-1`：成员在当前阶段截止前加入，OC不停转；
- `Tn > Rn-1`：OC已经停转，从成员实际加入时间重新启动24小时。

### 3.2 标准示例

六人 `Break the Bank`：

```text
A 07-17 07:00加入
→ readyTime = 07-18 07:00
→ 理想完成 = 07-23 07:00

B 07-17 15:00加入，早于07-18 07:00
→ readyTime = 07-19 07:00
→ 理想完成仍为07-23 07:00

C 07-19 09:00加入，晚于07-19 07:00
→ OC已停转
→ readyTime = 07-20 09:00
→ 理想完成变为07-23 09:00
```

### 3.3 成员占用

成员从实际 `joinAt` 开始占用，直到该OC最终 `readyTime` 才释放。

同一成员不能在重叠时间参加多个OC。

---

## 4. 方案B：分阶段无停转准入

本轮新增OC不能要求所有成员现在同时空闲，也不能让OC长期等待未来成员。

正确准入规则是：

```text
第一位：当前可加入
第二位：第一阶段readyTime前可加入
第三位：第二阶段readyTime前可加入
第四位：第三阶段readyTime前可加入
……
```

例如当前时间为07-17 07:00：

```text
A现在可用
B在20小时后释放
C在47小时后释放
```

对于三人OC：

```text
A现在加入 → 第一阶段截止24小时后
B在20小时后加入 → 第二阶段截止48小时后
C在47小时后加入 → 未超过48小时截止
```

该OC可无停转承接。

如果C在49小时后释放，则超过第二阶段截止，判定不可用于本轮安全证明。

### 4.1 已停转的现有OC

如果现有OC的 `readyTime` 已早于快照时间，下一位成员可在快照时刻恢复一次；恢复后的后续成员必须在新的阶段截止前加入，不允许再次新增停转。

### 4.2 7天规则

7天仅约束空OC第一位成员的最晚加入时间，是合法性兜底，不是主要容量来源。

对于本轮新增OC，第一位成员本身要求当前可加入，因此正常情况下7天条件不会成为主要约束。

高阶后继从前置实际完成时获得新的7天首人加入窗口。

## 5. 岗位、成员和阶段的联合搜索

无停转准入不能逐阶段随便选一个人，否则可能提前消耗唯一能承担稀缺岗位的成员。

`OcRosterMatcher.matchWithoutPause()` 使用有界回溯，联合搜索：

```text
剩余岗位
× 当前阶段截止前可用成员
× 成员岗位能力
× 后续阶段截止时间
```

每个搜索节点：

1. 计算当前阶段最晚加入时间；
2. 枚举截止前可加入且岗位达标的成员—岗位组合；
3. 选择一组后移除对应成员和岗位；
4. `readyTime` 顺延24小时；
5. 搜索剩余岗位；
6. 后续无解时回溯。

候选顺序优先考虑：

1. 当前阶段合格成员更少的岗位；
2. 更早释放的成员；
3. 能力覆盖更少的成员；
4. 岗位优先级；
5. 用户ID，保证结果稳定。

技术保护：

```text
MAX_NO_PAUSE_SEARCH_NODES = 20_000
```

找到完整排程即证明安全；预算内未找到只表示当前保守搜索未证明可行，不能反向宣称数学上绝对不可行。

普通 `match()` 和基础时间线的确定性匹配仍保留，不与本轮无停转联合搜索混淆。

## 6. 当前批次成员隔离

刷新建议代表“现在可以承接的批次”，不能依赖同一批成员完成一支新增OC后再去完成另一支已经刷出的OC。

本轮维护 `reservedMemberIds`：

- 不同新增普通OC之间禁止复用成员；
- 普通OC与新增高阶链之间禁止复用成员；
- 不同新增高阶链之间禁止复用成员；
- 同一高阶链内部允许前置完成后复用成员到自己的后继。

现有计划OC完成后释放的成员，可以用于本轮新增OC，只要该成员能在对应准备阶段截止前加入。

本轮新增OC 1完成后释放的成员，不能用于证明本轮新增OC 2安全。

该规则区分：

- 静态互不复用完整阵容数；
- 当前批次安全刷新数；
- 长期串行吞吐量。

长期串行吞吐量不得作为当前刷新建议。

## 7. 普通池与高阶池联合安全前沿

普通池和高阶池都可能连续刷新多次，必须联合验证向量：

```text
(normalCount, highCount)
```

### 7.1 普通池

对指定普通刷新次数，枚举计划内普通类型的全部多重集合组合。

只有所有随机结果组合都能在共享成员时间线上无停转承接，该普通刷新次数才安全。

### 7.2 高阶池

对指定高阶刷新次数，枚举计划内高阶根类型的全部组合。

每条高阶结果必须验证：

```text
根节点 → 全部后继节点
```

链内允许成员复用，链间禁止复用。

### 7.3 笛卡尔积

最终验证：

```text
所有普通结果组合 × 所有高阶链结果组合
```

任一组合失败，刷新向量失败。

### 7.4 搜索保护

```text
单次求解时间预算：1000ms
单池搜索上限：20
```

这些是技术保护，不是业务最大值。

超时或达到上限时，只返回已证明安全下界，并明确输出警告。

---

## 8. 三种模式

三种模式从同一个已证明安全前沿选点，不运行不同的岗位算法。

默认容量比例：

```text
保守：25%
均衡：50%
收益：100%
```

比例按整数严格向下取整，不强制至少刷新一次。

- 保守：普通池优先；
- 均衡：普通与高阶尽量平衡；
- 收益：高阶次数优先，再考虑总次数。

策略解析顺序：

```text
当前帮派策略
→ faction_id = 0 全局策略
→ 字段未配置时使用代码默认值
```

显式非法配置是硬错误，必须输出0并停止建议，不能用默认值掩盖错误。

---

## 9. 配置与高阶链门禁

以下情况必须 fail-closed：

- 计划内高阶根没有链定义；
- 链序号不从1连续；
- 前一条边的child与后一条边的parent不连续；
- 链内节点重复；
- 多条链共享同一个计划内根；
- 计划链节点档案缺失；
- 节点不是 `READY`；
- 岗位模板为空；
- 节点被Catalog标记为invalid；
- 策略容量比例显式非法。

计划范围外的断链不影响当前帮派。

配置硬错误时：

```text
普通池 = 0
高阶池 = 0
```

并在警告区说明原因。

## 10. 当前现实占用摘要

用户需要看到当前有多少现实队伍、占用了多少达标成员，而不是求解器内部算法步骤。

默认输出 `【当前OC占用】`：

- 当前队伍：全部现实 `Recruiting / Planning` OC；
- 已有人队伍：至少一个岗位已有成员；
- 无人队伍：所有岗位均无人；
- 实际占用成员：全部现实OC中已加入的去重成员；
- 达标成员：满足任一计划内OC岗位实际门槛的当前帮派成员；
- 已占用达标成员：现实占用成员与达标成员的交集；
- 空闲达标成员：达标成员减去现实占用成员。

岗位实际门槛按以下优先级确定：

```text
帮派自定义岗位成功率门槛
→ 未覆盖时使用全局岗位成功率门槛
```

达标不是单一成功率数字，也不是帮派总人数；成员至少满足一个当前计划内、`READY`且配置有效的OC岗位门槛才计入。

求解器的阶段准入、安全前沿和随机组合继续作为内部安全约束，但不在默认输出中逐条展示。配置错误、超时和搜索上限仍在警告区显示。

```text
【当前OC占用】
- 当前队伍: 27个（已有人25个 / 无人2个）

- 已占用达标成员: 62人

```

## 12. 核心实现结构

命令调用链：

```text
OcNewTeamStrategyImpl
→ OcNewTeamPlanningFacade
→ OcRefreshInstructionPlanner
→ OcRefreshSafetyRequestFactory
→ OcRefreshSafetySolver
→ OcRefreshModeSelector
→ OcNewTeamPlanRenderer
```

核心职责：

- `OcPlanningSnapshotLoader`：批量加载不可变快照；
- `OcRefreshSafetyRequestFactory`：按计划范围构造基础需求、普通模板和高阶链；
- `OcChainPlanningService`：构造并校验完整高阶链；
- `OcRosterMatcher`：岗位匹配、readyTime递推和方案B联合回溯；
- `OcRefreshSafetySolver`：基础时间线、随机组合、批次隔离和安全前沿；
- `OcCurrentOccupancyCalculator`：统计全部现实OC和达标成员占用摘要；
- `OcRefreshModeSelector`：按模式容量比例从同一安全前沿选点；
- `OcRefreshInstructionPlanner`：组装刷新指令、现实占用摘要和警告；
- `OcNewTeamPlanRenderer`：渲染最终文本。

求解循环内禁止访问数据库，不得产生N+1查询。

## 13. 数据同步与环境隔离

生产环境在规划前同步Torn API数据：

```java
BotConstants.ENV_PROD.equals(projectProperty.getEnv())
```

非生产环境使用订阅数据，跳过主动同步，避免主键冲突和破坏逻辑订阅。

程序只同步数据和生成指令，不能执行游戏内刷新。

## 14. 测试与验收重点

必须覆盖：

1. `readyTime`提前加入与停转恢复；
2. 第一人当前加入；
3. 第二人在24小时阶段前释放；
4. 第三人在48小时阶段前释放；
5. 超过对应阶段截止时拒绝；
6. 稀缺岗位成员保留；
7. 计划内无人OC占容量；
8. 非计划无人OC不占容量、不展示；
9. 不同新增OC之间禁止成员复用；
10. 同一高阶链内部允许根到后继复用；
11. 普通与高阶随机结果笛卡尔积；
12. 共享根、断链、缺链、非READY和无岗位模板fail-closed；
13. 模式比例严格向下取整；
14. 超时只返回安全下界；
15. 输出包含全部现实OC数量和成员占用；
16. 达标成员按帮派岗位门槛覆盖后的实际门槛筛选；
17. 输出不包含成员、岗位和个人时间；
18. JDK21编译、Javadoc doclint、Liquibase增量和真实只读回放。

## 15. 已废弃设计

以下旧设计不得恢复：

- 输出具体成员、岗位和加入时间；
- 旧队补位指令；
- Beam Search成员排班方案；
- Pareto成员人天计划；
- 固定“安全并行20条”；
- 无限未来串行复用作为当前并发容量；
- 普通池和高阶池分别求最大后相加；
- 用7天期限放大当前刷新容量；
- 非计划无人OC占用成员容量；
- 显式非法配置自动回退后继续输出非零建议。

本文件是当前OC新队功能的最终业务与技术设计基线。后续修改必须同步更新本文档，并重新执行专项测试、真实只读回放和质量门禁。
