## 1. 产品定位

`OC新队` 是面向OC指挥官的**匿名人工刷新决策器**。

系统根据当前OC状态、成员岗位能力、成员释放时间、准备阶段、高阶链义务和计划范围，计算本轮建议人工执行的：

```text
(普通池刷新次数, 高阶池刷新次数)
```

指令只提供刷新决策，不代替指挥官执行游戏操作。

### 1.1 允许输出

- 快照时间；
- 普通池建议刷新次数；
- 高阶池建议刷新次数；
- 当前现实OC数量、已有人队伍数和无人队伍数；
- 当前实际占用成员数；
- 达标成员、已占用达标成员和空闲达标成员数量；
- 当前是否存在全帮卡死或被迫拆队风险；
- 是否仍有确定的正常完成—成员释放路径；
- 下一批关键释放时间；
- 下次重新评估时间和最晚重新评估时间；
- 建议属于保守、均衡还是收益取向；
- 是否允许有明确恢复点的短时停转；
- 是否仅得到已证明安全下界；
- 匿名的配置、规划和风险说明。

### 1.2 禁止输出

- 成员姓名；
- 具体岗位；
- 个人加入时间；
- 旧队补位动作；
- 成员人天明细；
- 高阶链内部运行状态；
- 固定“安全并行N条”等会过时的数字；
- 自动刷新成功、自动补位成功等虚假表述。

成员、岗位和时间安排可以作为内部可行性证明，但不得变成对外排班指令。

### 1.3 人工操作边界

普通池和高阶池是两个独立的游戏内人工刷新入口，均可连续操作多次。

系统可以同步数据和生成建议，但不能替用户点击游戏刷新、选择随机结果或安排成员加入。

每次完成刷新后，应立即重新运行指令，以新的真实随机结果重新评估。

## 2. 规划范围

一个OC只有同时满足以下业务条件，才属于当前帮派自动规划范围：

```text
帮派明确启用
+ OC业务资料达到可规划状态
+ 岗位要求有效
+ 高阶链关系完整
```

### 2.1 计划内OC

- 计划内有人OC：已有成员和岗位固定，不移动、不换岗，只证明剩余岗位、完成路径和后继义务；
- 计划内无人OC：属于未来待启动义务，占未来规划容量，但尚未加入成员前不占真实成员；
- 计划内高阶根：一旦有人加入，必须同时保障完整后继链义务；
- 新增OC和新高阶链应通过业务配置进入范围，不应要求修改规划规则本身。

### 2.2 非计划OC

- 非计划无人OC：不占成员容量，不作为刷新建议必须承接的义务；
- 非计划有人OC：不自动补位、不调整成员，但真实占用持续到成员正常释放；
- 非计划有人OC的释放时间应尽量使用真实可证明时间，不应无证据统一延后。

### 2.3 当前帮派规划范围

规划范围必须动态读取当前业务配置，不能把OC名称或数量写死。

2026.08.15业务快照：

#### NOV

可直接刷新的计划根共7个：

- 普通池4个：`Blast from the Past`、`Window of Opportunity`、`Break the Bank`、`Clinical Precision`；
- 高阶根3个：`Lock Stock`、`Manifest Cruelty`、`Stacking the Deck`。

启用链节点包括：`Ace in the Hole`、`Gone Fission`、`Hostile Takeover`、`Crane Reaction`。

#### PN

可直接刷新的计划根共6个：

- 普通池4个：`Blast from the Past`、`Window of Opportunity`、`Break the Bank`、`Clinical Precision`；
- 高阶根2个：`Lock Stock`、`Stacking the Deck`。

启用链节点包括：`Ace in the Hole`、`Hostile Takeover`。

这些数量只是当前业务快照，不是永久常量。长期文档和规划结果都应随配置变化更新。

## 3. 首要安全目标：防止全帮卡死

OC安全规划最需要避免的，不是任意一支队伍发生短时停转，而是**成员流动性枯竭**：

- 大量成员被分散锁进未满员OC；
- 当前没有足够空闲成员补齐关键缺口；
- 未来没有任何队伍能正常完成并释放成员；
- 或未来释放人员无法承担真正缺少的岗位；
- 最终只能拆解已有进度队伍，才能恢复成员流动。

### 3.1 典型场景

```text
达标成员：100人
同时运行OC：30支
总岗位：130个
每支OC都缺1人
```

```text
岗位总缺口 = 130 - 100 = 30个
平均每支OC已有成员 = 100 / 30 ≈ 3.33人
```

如果100名成员全部进入30支未满员OC，并且没有任何一支能够正常完成：

- 当前空闲达标成员为0；
- 未来没有确定释放事件；
- 所有队伍都在等待补位；
- 只能拆解已有进度队伍释放成员。

这属于全帮卡死或被迫拆队风险。

### 3.2 核心不变量

每次建议刷新、启动新OC或重新分配释放成员后，必须继续满足：

```text
未来仍存在至少一条
“不拆解已有进度队伍”的正常完成—成员释放路径。
```

如果不存在这样的路径：

- 普通池和高阶池新增建议均为0；
- 必须明确提示“当前存在全帮卡死或被迫拆队风险”；
- 不能只用“剩余达标成员不足”掩盖真实原因。

### 3.3 不能只看当前空闲人数

当前空闲人数为0，不一定代表卡死。

如果08:00有一支完整队伍正常完成并释放合格成员，当前状态属于高负载运行，仍具有正常流动性。

是否可恢复必须同时验证：

- 释放时间；
- 释放成员岗位能力；
- 关键缺口；
- 高阶链义务；
- 不可逆期限；
- 后续是否还能继续形成新的完成—释放事件。

### 3.4 流动性锚点

时间线上至少保留一个可证明的流动性锚点：

- 已满员且会正常完成的队伍；
- 已证明能够补齐并在确定时间完成的队伍；
- 会在关键期限前释放稀缺岗位成员的队伍；
- 其他能形成下一轮正常释放的确定事件。

不能把所有成员分散投入没有任何一支能够率先完成的队伍。

流动性锚点保护的是连续释放能力，不是永久保护某一支OC、某一批成员或某个岗位。允许当前锚点完成后，其释放成员投入另一支OC，并由后者在原释放链条断裂前成为新的锚点。任何锚点替换都必须在同一有限时间线内证明完整完成—释放路径，不能只证明释放成员“能做某一个岗位”。

## 4. 安全目标优先级

### 4.1 第一优先级：禁止被迫拆队

所有模式共同遵守：

- 不移动已有成员；
- 不调整已有岗位；
- 不允许规划把帮派推进到只能拆已有进度队伍才能恢复流动性的状态。

### 4.2 第二优先级：保护已投入义务和完整高阶链

以下属于硬义务：

- 已有人OC的既有投入；
- 已启动高阶根的完整后继链；
- 错过后会导致链失败、既有进度无法恢复或必须拆队的期限。

已经启动的高阶链必须按完整链保障，不能只看根节点能否开始。

### 4.3 第三优先级：管理计划内无人OC过期

计划内无人OC需要纳入时间线，但它与已有人OC的硬义务不同：

- 无人OC尚未锁定成员；
- 没有已投入准备进度；
- 单支自然过期不是全帮安全事故；
- 过期会损失刷新机会和潜在收益，属于待启动刷新价值损失。

正常运行时，应通过合理的新队数量、持续成员释放和重新评估节奏，使计划内目标OC原则上不发生可避免过期。

如果启动某支无人OC会造成被迫拆队、已启动链失败或流动性枯竭，允许该无人OC过期，不能为了追求“零过期”制造更严重风险。

计划内目标OC频繁过期，说明至少存在以下问题之一：

- 刷新数量过高；
- 规划范围过宽；
- 当前成员能力不足；
- 时间线估算不准确；
- 未按重新评估窗口执行；
- 业务配置需要调整。

### 4.4 第四优先级：允许可恢复停转

普通准备阶段停转不一定等于经济失败。

如果一支队伍14:00停转，16:00有合格成员正常释放并可补入，则该队伍可能只发生2小时可恢复停转。

允许可恢复停转必须同时满足：

- 不需要拆解其他已有进度队伍；
- 未来释放成员满足对应岗位门槛；
- 不错过已投入义务的硬期限；
- 不阻断已启动高阶链；
- 仍保留正常完成—释放路径；
- 接受停转后的总体价值不低于立即补位方案。

```text
禁止被迫拆队是硬约束；
是否允许短时停转是经济选择。
```

### 4.5 第五优先级：减少空闲和机会损失

成员正常释放后长期闲置，也会造成收益和流动性损失。

释放成员应从释放时刻重新进入全局候选池，并与当时的全部待办OC重新比较。

## 5. 准备阶段与成员占用

`readyTime` 表示当前累计准备阶段结束、可以进入下一阶段的时间，不等同于整支队伍天然完成时间。

### 5.1 业务递推

无人加入时：

```text
readyTime = null
```

第一位成员在 `T1` 加入：

```text
R1 = T1 + 24小时
```

后续成员在 `Tn` 加入，上一阶段时间为 `Rn-1`：

```text
Rn = max(Tn, Rn-1) + 24小时
```

- `Tn <= Rn-1`：成员在当前阶段结束前加入，不新增停转；
- `Tn > Rn-1`：队伍已经停转，从实际加入时间重新开始24小时。

### 5.2 标准示例

六人 `Break the Bank`：

```text
A 07-17 07:00加入
→ readyTime = 07-18 07:00
→ 理想完成 = 07-23 07:00

B 07-17 15:00加入，早于07-18 07:00
→ readyTime = 07-19 07:00
→ 理想完成仍为07-23 07:00

C 07-19 09:00加入，晚于07-19 07:00
→ 队伍已停转
→ readyTime = 07-20 09:00
→ 理想完成变为07-23 09:00
```

### 5.3 成员占用

成员从实际加入时间开始占用，直到该OC最终完成并释放。

唯一绝对复用规则：

```text
同一成员的实际占用时间区间不能重叠。
```

成员不能在重叠时间参加多个OC，但可以在前一支OC正常完成后参加其他OC。

## 6. 事件驱动的成员时间线

规划应围绕真实业务事件重新评估，而不是只看当前静态空闲人数。

### 6.1 关键事件

- 当前快照时间；
- OC正常完成并释放成员；
- 准备阶段边界；
- 预计停转；
- 停转恢复；
- 高阶链后继生成；
- 计划内无人OC接近过期；
- 新随机结果出现；
- 用户重新运行指令。

### 6.2 释放后重新进入候选池

只要成员在08:00正常释放，就应从08:00起参与全部待办OC的重新规划。

禁止以下静态做法：

- 因为成员在当前快照被占用，就在整个建议批次永久不可用；
- 因为成员曾用于某支未来OC的内部证明，就永久预留给该OC；
- 因为某支队伍未来可能需要该成员，就禁止其在不重叠时间加入其他OC。

### 6.3 动态比较

每次关键事件后，应重新比较：

- 哪些队伍即将停转；
- 哪些已投入义务接近硬期限；
- 哪些计划内无人OC接近过期；
- 哪些队伍补入后可以最早完成并形成下一轮释放；
- 哪些岗位最稀缺；
- 哪个选择的增量成员人天更低；
- 哪个选择的边际收益更高；
- 哪个选择最能维持全局流动性。

不能为保持局部某一支队伍不停转，而破坏整体成员周转。

## 7. 下次重新评估窗口

每次规划的业务证明范围限定为：

```text
当前真实快照时间 ～ 最晚重新评估时间
```

系统只对该有限窗口内的时间线作出承诺，不主张窗口结束后原建议仍然成立。刷新、随机结果变化或其他事实改变会立即使旧建议失效。

每个非终态建议必须输出：

```text
建议下次重新评估时间 ～ 最晚重新评估时间
```

### 7.1 下次重新评估时间

表示最早会实质改变建议的确定事件，例如：

- 下一支OC正常完成并释放成员；
- 高阶链后继生成；
- 新随机结果出现；
- 已停转OC进入可恢复节点；
- 其他会改变岗位可用性的确定事件。

### 7.2 最晚重新评估时间

表示继续沿用当前建议的最后边界，例如：

- 已投入义务不可逆期限；
- 下一支队伍停转边界；
- 计划内无人OC启动截止或过期时间；
- 流动性锚点可能消失的时间；
- 当前业务证明不再成立的其他边界。

### 7.3 执行规则

1. 执行任何刷新后立即重新运行指令，不等待旧窗口；
2. 没有提前变化时，最晚必须在窗口上界前重新运行；
3. 最早有效事件晚于最晚安全边界时，不能输出等待建议；
4. 阶段一操作提前量固定为30分钟，最晚重新评估时间应在业务边界前30分钟；
5. 若随机结果已经变化，下次重新评估时间为当前时间；
6. 该窗口用于人工重新运行指令，不代表系统自动执行刷新。

示例：

```text
建议重新评估窗口：16:00 ～ 18:00前
原因：16:00释放关键成员；18:00存在下一支队伍停转边界
```

## 8. 收益与成员人天

### 8.1 总体目标

收益模式应在硬安全边界内比较规划时间窗的全局净价值：

```text
全局净价值
= 保住的预期OC收益
+ 新增OC预期收益
+ 避免拆队的损失
+ 提前形成下一轮成员释放的价值
- 可恢复停转损失
- 已投入义务失败损失
- 无人OC过期损失
- 成员机会成本
- 全帮卡死风险成本
```

该表达定义业务组成，不代表所有数值已经冻结。

### 8.2 简单业务先验

缺少精细收益证据时，先使用稳定业务先验：

```text
通常等级更高，总收益更高；
同等级下，通常需要成员更多，总收益更高。
```

但该先验只用于总收益初步判断。实际时间线争夺的是成员在一段时间内的使用权，必须同时考虑成员人天。

### 8.3 标准成员人天

按逐阶段加入模型，满编 `N` 人OC的标准成员人天为：

```text
N × (N + 1) / 2
```

- 4人、4天OC：10成员人天；
- 5人、5天OC：15成员人天；
- 6人、6天OC：21成员人天。

具体快照中，已有成员、当前进度、未来加入时间和停转会改变剩余成本，最终应比较：

```text
增量剩余成员人天
```

不能永远使用标准满编值。

### 8.4 四个业务示例

2026.08.15只读业务样本按完整收益和标准成员人天验证：

| OC | 等级 | 人数 | 标准成员人天 | 完成尝试 | 成功样本 | 平均成功收益 | 平均成功收益/人天 | 观察收益/尝试人天 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Ace in the Hole | 9 | 5 | 15 | 57 | 40 | 473,793,050 | 31,586,203 | 22,165,757 |
| Break the Bank | 8 | 6 | 21 | 1,677 | 1,306 | 310,606,149 | 14,790,769 | 11,518,631 |
| Clinical Precision | 8 | 4 | 10 | 1,663 | 1,278 | 101,651,616 | 10,165,162 | 7,811,832 |
| Blast from the Past | 7 | 6 | 21 | 2,453 | 1,968 | 146,097,645 | 6,957,031 | 5,581,507 |

当前示例排序为：

```text
Ace in the Hole
> Break the Bank
> Clinical Precision
> Blast from the Past
```

`Clinical Precision` 虽然总收益低于 `Blast from the Past`，但标准成员人天为10，后者为21，因此单位成员人天收益明显更高。

四个OC只是业务解释示例，不是完整规划范围。

### 8.5 收益比较层级

比较两个可行时间线时：

1. 先满足禁止被迫拆队、已启动链硬义务和岗位时间线可行性；
2. 再比较规划窗口内的预期总收益；
3. 成员或时间冲突时，比较增量单位成员人天收益；
4. 结果接近时，优先更早完成并更早释放稀缺岗位成员的方案；
5. 仍无法区分时，才酌情使用更复杂的历史证据和不确定性修正。

“高级优先、同级多人优先”是简单先验和缺数据时的稳定回退，不是忽略人天的最终比较器。

### 8.6 高阶根按完整链评价

高阶根不能只按根节点直接奖励评价。

其业务价值应包含：

- 根节点本身；
- 成功后生成的全部后继节点；
- 完整链所需成员人天；
- 高阶链硬义务；
- 链完成带来的总收益和流动性影响。

高阶根直接奖励缺失或为0，不代表完整链没有价值。

### 8.7 复杂收益证据的使用边界

复杂收益证据只在以下场景酌情使用：

- 同等级、同人数、成员人天接近的OC需要进一步排序；
- 简单先验与长期稳定的人天收益证据明显冲突；
- 比较短时停转、等待和提前释放价值；
- 高阶根需要评价完整链；
- 新OC资料不足；
- 业务专家明确要求精细收益复核。

复杂收益证据只能作为必要修正或同级决胜依据，不恢复无必要的复杂预测链路。

历史帮派成功率不得替代当前成员岗位能力。

## 9. 08:00、14:00、16:00、18:00示例

假设：

```text
队伍A：08:00完成，释放一批成员
队伍B：16:00完成，释放另一批成员
队伍C：14:00若无人补位会停转
队伍D：18:00若无人补位会停转
```

时间关系：

```text
08:00 → 14:00：6小时
08:00 → 16:00：8小时
14:00 → 16:00：2小时
16:00 → 18:00：2小时
```

### 9.1 不能使用的机械规则

- 08:00释放成员必须优先加入最早停转的队伍C；
- 队伍C会在14:00停转，就必须从08:00永久预留成员；
- 为保证所有队伍无停转，拒绝任何更高价值机会。

### 9.2 方案一：08:00补队伍C

可能获得：

- 避免C在14:00停转；
- C可能更早完成。

可能付出：

- 08:00释放成员不能投入其他更高价值OC；
- 16:00释放成员可能闲置或只能投入次优目标。

### 9.3 方案二：08:00投入其他目标，16:00恢复C

可能获得：

- 08:00成员提前8小时投入更高价值目标；
- 16:00成员恢复C；
- 16:00成员仍可能在18:00前处理D。

可能付出：

- C从14:00到16:00发生2小时可恢复停转。

方案二只有在以下条件全部成立时才可选择：

- 不拆解其他已有进度队伍；
- 16:00释放成员满足C的岗位门槛；
- C不会错过硬义务期限；
- 不阻断更高优先级高阶链；
- 增益超过2小时停转损失；
- 仍保留正常完成—释放路径。

### 9.4 示例结论

收益模式不是让所有队伍永不停转，也不是让尽可能多人立刻加入。

```text
在不造成被迫拆队、硬义务失败和全帮卡死的前提下，
允许部分队伍发生可恢复短时停转，
以换取更高的全局净收益。
```

具体选择必须依据真实时间线、岗位能力、增量成员人天和收益证据，不能固定选择某一方案。

## 10. 三种模式的业务语义

三个模式使用同一事实快照、同一成员时间线和同一硬安全底线。差异来自停转容忍、流动性余量和收益目标，不应只是25%、50%、100%的机械缩放。

### 10.1 保守模式

目标：降低人工协调和时间线波动。

- 禁止被迫拆队；
- 保护已投入义务和完整高阶链；
- 优先选择不引入新停转的时间线；
- 保留稀缺岗位与流动性余量；
- 已证明至少可安全刷新1次时，不应仅因比例向下取整返回0；
- 普通池优先，但不能忽略高阶链硬义务。

### 10.2 均衡模式

目标：平衡流动性安全和成员利用率。

- 禁止被迫拆队；
- 允许有明确恢复时间和合格释放成员的短时停转；
- 不错过已投入义务的硬期限；
- 计划内无人OC原则上在过期前启动，但不能以制造卡死为代价；
- 优先形成持续的完成—释放—再投入循环；
- 普通池与高阶池根据当前时间线和成员人天平衡，而非机械要求数量相等。

### 10.3 收益模式

目标：在硬安全边界内提高全局净收益。

- 禁止被迫拆队，不能为收益突破；
- 已启动高阶链按完整链保障；
- 允许经济上合理的可恢复停转；
- 释放成员按边际收益、增量成员人天和流动性重新分配；
- 高阶优先不能覆盖真实岗位稀缺性和时间线；
- 只有证据支持时，才能声称某方案收益更高；
- 不能用固定比例冒充收益优化。

### 10.4 阶段一已冻结业务政策

以下规则适用于本轮首次实施和Shadow验收；后续获得更充分证据后可按业务审批流程调整。

#### 重新评估操作提前量

```text
操作提前量 = 30分钟
```

- 最晚重新评估时间按业务边界提前30分钟；
- 若计算后的最晚时间不晚于当前时间，输出“现在重新评估”；
- 刷新或随机结果已经变化时立即重新评估，不再沿用旧窗口。

#### 保守模式停转政策

- 不允许规划主动制造新的停转；
- 已经停转的队伍仍可在不破坏硬义务和流动性的前提下恢复；
- 已证明至少可安全刷新1次时，不因固定比例向下取整变成0。

#### 均衡模式停转政策

允许普通计划OC发生可恢复停转，但必须同时满足：

- 单次主动新增停转不超过6小时；
- 已存在确定的正常释放事件；
- 释放时存在完整、岗位适配的恢复路径；
- 不涉及已启动高阶链节点；
- 不跨越已投入义务硬期限；
- 不破坏流动性锚点；
- 不增加计划内无人OC的可避免过期；
- 相比无停转方案，能形成更高业务价值或更早的完整释放事件。

#### 收益模式停转政策

允许普通计划OC发生更积极的可恢复停转，但必须同时满足：

- 单次主动新增停转不超过12小时；
- 已存在确定的正常释放事件和完整岗位恢复路径；
- 不涉及已启动高阶链节点；
- 不违反硬义务、流动性和无人OC过期边界；
- 候选时间线按已冻结价值比较顺序严格优于无停转方案。

阶段一不允许规划主动制造已启动高阶链节点的新增停转。已经发生的停转可以恢复，但不得以其作为扩大刷新次数的未证明容量。

#### 停转方案的输出权限

阶段一允许均衡和收益模式依据上述明确规则直接选点，不要求每个候选都转为人工复核；但：

- 只能表述为“按当前业务价值顺序选择”；
- 不能声称已经证明具体金额收益更高；
- 若完整链、收益证据或恢复路径不足以完成比较，则标记经济证据不足，不得因该候选提高刷新建议。

#### 待启动无人OC队列

阶段一不设置固定数量上限，采用动态可行性控制：

- 所有计划内待启动无人OC必须同时进入时间线；
- 每支均需在首人期限前存在可行启动或重新评估路径；
- 不得破坏硬义务和流动性锚点；
- 只要新增刷新会产生不可避免过期、集中开工风险或未证明义务，就停止增加刷新次数；
- 后续若生产运营证明仍需要人工数量上限，再单独提交业务审批。

#### 价值证据不足时的降级顺序

对普通OC或完整高阶链，按以下顺序选用价值证据：

1. 样本达到业务最低样本数且奖励数据完整时，使用观察每次尝试收益，并结合当前增量剩余成员人天；
2. 样本不足但存在正的可靠收益下界时，使用收益下界，并结合当前增量剩余成员人天；
3. 金额证据仍不足时，使用业务先验：完整候选所达到的最高等级、完整链总需人数、链节点数量、增量剩余成员人天、预计释放时间；
4. 仍无法稳定区分时，标记经济证据不足，不得声称收益最优，也不得据此主动增加停转或刷新次数。

高阶根始终按根和全部后继组成的完整链参与上述判断，不能因根节点直接奖励为0而降为无价值。

## 11. 随机刷新与计划内无人OC

### 11.1 刷新不等于立即开工

随机刷新后出现的无人OC可以暂时保持无人状态。

判断刷新是否可接受时，应区分：

- 刷出该OC是否立即锁定成员；
- 是否必须现在启动；
- 最晚何时需要启动；
- 启动窗口内是否有合格成员正常释放；
- 留空等待是否影响已有义务；
- 同时待启动数量是否超过可管理范围。

不能要求每一个可能随机结果都在当前时刻立即静态冻结一套完全隔离的完整阵容。

### 11.2 计划内无人OC占未来容量

计划内无人OC应记录并参与：

- 过期时间；
- 岗位需求；
- 预计启动窗口；
- 与未来释放成员的岗位匹配；
- 待启动队列压力；
- 未来时间点的集中开工风险。

计划内无人OC占未来规划容量，但未加入成员前不占真实成员。

### 11.3 随机结果风险边界

- 保守模式：所有允许随机结果都应存在不拆队、尽量不停转的可行时间线；
- 均衡模式：所有允许随机结果都不得造成被迫拆队，允许留空等待或有恢复点的短时停转；
- 收益模式：同样禁止被迫拆队，在数据充分时按概率、留空成本、完整链价值、增量人天和恢复时间选择更高价值刷新次数。

当概率、成本或收益证据不足时，不得给出未经证明的额外收益刷新次数。

## 12. 输出解释要求

输出必须让指挥官理解为什么建议为0、1或更多，同时保持匿名。

结果必须分别表达以下业务维度，不能混成单一状态：

- 配置是否有效、完整；
- 时间线是已证明安全、已证明不可行，还是因超时、预算或规划未找到而未证明；
- 当前存在的业务风险；
- 已证明安全刷新下界及其是否只是下界；
- 匿名、稳定的主要原因。

只有确定性矛盾或有限窗口内完成无截断可行性检查后证明无解，才能表述为“已证明不可行”或“已证明存在被迫拆队风险”。超时、预算耗尽、固定顺序失败或启发式未找到，只能表述为“当前预算内未证明”，可以保守停止刷新，但不能冒充已证明无路径。

至少说明：

- 当前是否存在全帮卡死或被迫拆队风险；
- 当前已有人但未满员OC数量；
- 是否仍有确定的正常释放锚点；
- 下一批关键释放时间；
- 普通池和高阶池建议次数；
- 当前模式是否允许可恢复停转；
- 是否只得到安全下界；
- 主要阻断类型；
- 下次重新评估时间；
- 最晚重新评估时间。

示例：

```text
当前不存在被迫拆队风险。
下一批关键成员预计16:00释放。
收益模式允许一支队伍发生最多2小时可恢复停转；该选择需要收益证据支持。
建议重新评估窗口：16:00 ～ 18:00前。
若提前完成刷新或随机结果发生变化，应立即重新运行指令。
```

不得在缺少经济证据时输出“允许停转更赚钱”。

## 13. 实施前置业务答卷

本节是实施方案评审的业务门禁，不是实施过程中的可选思考题。

执行顺序：

```text
技术专家逐项作答并给出业务规则、数据或回放证据
→ 业务专家逐项确认、修订或冻结缺失口径
→ 技术专家制定详细实施方案
→ 用户明确授权“开始实施/可以实施”
→ 才能开始实施变更
```

当前阶段一业务参数已经在第10.4节冻结。技术专家的详细实施方案必须逐项映射这些参数，不得自行替换、放宽或扩张。

要求：

- 每个问题必须明确回答，不能写“实施时再看”；
- 缺少业务参数时标记待业务冻结，实施人员不得自行猜测；
- 需要事实证据时使用只读查询或真实回放；
- 业务专家确认答卷不等于实施授权；
- 实施中发现答案错误或业务变化时，停止对应工作并返回答卷和方案阶段。

### 必答问题

1. 如何定义并检测“如果不拆已有进度队伍，就不存在下一次正常成员释放”的卡死状态？
2. 如何证明规划后始终保留至少一个完成—释放的流动性锚点？
3. 如何将人数约束升级为成员—岗位—时间联合规划？
4. 计划内无人OC如何占未来容量，而不是当前静态冻结完整阵容？
5. 成员在关键时间释放后，如何重新参与全部待办OC？
6. 如何保证成员只禁止时间区间重叠，而不是整批永久禁用？
7. 如何区分已投入义务硬期限、无人OC过期和普通可恢复停转？
8. 如何评价可恢复停转的经济损失？
9. 如何评价拆解已有进度队伍的损失？
10. 如何评价提前释放稀缺岗位成员的流动性价值？
11. 如何组合等级、人数、增量成员人天和完整链价值形成稳定、可审核的收益比较？
12. 如何动态覆盖当前帮派全部启用计划根和完整后继链，不写死OC名单与数量？
13. 随机结果允许留空多久、最多留空多少支、何时必须重新评估？
14. 如何计算下次重新评估时间和最晚重新评估时间？
15. 如何防止局部最优选择导致后续全帮卡死？
16. 如何区分真实不可行、规划未找到、预算耗尽和仅得到安全下界？
17. 如何通过真实只读回放证明建议不再过度保守，同时没有增加被迫拆队风险？

## 14. 业务验收场景

### 14.1 全帮卡死

给定：

- 100名达标成员；
- 30支OC；
- 130个岗位；
- 每支OC缺1人；
- 100名成员全部被占用；
- 没有任何队伍能正常完成并释放成员。

预期：

- 识别全帮卡死或被迫拆队风险；
- 两个刷新池新增建议均为0；
- 明确说明不存在正常释放路径。

### 14.2 高负载但可恢复

给定当前空闲成员为0，但08:00有完整队伍正常释放。

预期：

- 不误判为全帮卡死；
- 08:00释放成员重新进入全局候选池；
- 后续建议按08:00之后的时间线计算。

### 14.3 14:00停转、16:00恢复

给定：

- 08:00释放一批成员；
- C在14:00停转；
- 16:00释放另一批满足C岗位门槛的成员；
- C未接近硬义务期限。

预期：

- 保守模式可以优先避免停转；
- 均衡和收益模式可以比较立即补C与接受2小时停转；
- 只有价值证据支持时才能选择后者；
- 任一选择都不能要求拆解其他已有进度队伍。

### 14.4 18:00停转

给定D在18:00停转，16:00释放成员可以在边界前补入。

预期：

- 不在08:00机械永久预留成员给D；
- 允许16:00释放成员承担D；
- 08:00成员可以参与其他更高价值选择。

### 14.5 岗位不兼容

给定16:00会释放多人，但无人满足C的关键岗位门槛。

预期：

- 不能把释放人数视为C的恢复保障；
- 必须按真实岗位能力重新决策。

### 14.6 计划内无人OC

给定计划内无人OC尚有启动窗口，未来有确定成员释放。

预期：

- 占未来规划容量；
- 不立即冻结完整成员阵容；
- 根据释放和过期时间择时启动；
- 不得无限积累待启动OC。

### 14.7 收益与成员人天

给定 `Clinical Precision` 与 `Blast from the Past` 竞争同一批成员。

预期：

- 不只比较总收益或人数；
- 比较当前快照下的增量剩余成员人天；
- 能解释4人4天OC为何可能比6人6天OC更高效。

### 14.8 动态规划范围

预期：

- NOV当前覆盖7个可刷新计划根及其完整链；
- PN当前覆盖6个可刷新计划根及其完整链；
- 配置变化后范围自然更新；
- 不只支持四个示例OC。

### 14.9 三模式

同一快照下：

- 三模式使用同一事实时间线；
- 差异来自停转容忍、流动性余量和收益目标；
- 不能只通过固定百分比机械缩放；
- 已证明至少可安全刷新1次时，不能仅因向下取整变成0。

## 15. 验收与发布证据要求

项目没有历史OC成员能力快照时，不得伪造历史全量因果回放，也不能用单次当前快照声称已经证明长期生产安全。

验收证据分为四层：

1. 确定性业务夹具：覆盖卡死、高负载释放、锚点替换、有限非重叠复用、停转恢复、岗位不兼容、完整链、随机结果和证明状态区分；
2. NOV、PN当前真实只读回放：证明当前配置、成员能力、现实占用、启用计划根和完整链；
3. 实施后连续Shadow观察：在多个实际命令快照记录匿名规划摘要，观察被迫拆队、硬义务、停转、待启动压力、可避免过期和重新评估窗口；
4. 发布前业务Review：确认没有不可解释的安全退化，且均衡、收益模式没有突破已冻结政策。

Shadow仍基于指挥官实际运行命令和真实快照，不改变人工刷新、人工入队的产品边界。

当前真实只读回放至少比较：

- 修改前后建议次数；
- 当前空闲达标成员；
- 未来24小时和3天的正常释放成员；
- 释放成员岗位覆盖；
- 正常释放锚点；
- 被迫拆队风险；
- 可恢复停转数量和时长；
- 计划内无人OC可避免过期；
- 各模式最终选择；
- 增量剩余成员人天；
- 预期总收益与单位人天收益；
- 高阶根完整链价值；
- 重新评估窗口；
- 仅得到安全下界的比例。

必须证明：

```text
建议次数增加来自更准确的成员时间线、流动性判断和收益比较，
而不是删除全帮卡死保护或忽略高阶链硬义务；
计划内目标OC的可避免过期不增加；
全部启用计划根和完整后继链均被覆盖；
每个非终态建议都输出重新评估窗口。
```

## 16. 持续维护原则

本文是OC新队长期业务指导文档，应持续维护，不使用不可变或永久冻结式表述。

当以下事实变化时，应同步更新：

- 新OC或新高阶链加入；
- 帮派规划范围变化；
- 成员能力结构变化；
- 收益、人天或停转损失获得新证据；
- 三模式业务语义调整；
- 生产反馈发现新的流动性风险；
- 实际版本行为发生变化。

每次更新应区分：

- 当前生效规则；
- 尚待业务确认规则；
- 已废弃规则；
- 对应适用版本和验收状态。

一次性补充业务文档仅用于讨论、技术方案和验收。验收闭环后，应将有效规则合并进本文，再删除一次性文档。

## 17. 当前明确废弃的业务做法

- 将所有队伍永不停转作为唯一安全目标；
- 将第一人必须立即加入作为所有模式的唯一刷新准入；
- 同一批次永久禁止成员在不重叠时间复用；
- 把长期串行吞吐量称为当前安全并发容量；
- 固定“安全并行20条”或其他永久数字；
- 普通池和高阶池分别求最大后直接相加；
- 只用总人数而不考虑岗位能力；
- 只用总收益或人均收益而不考虑成员人天；
- 只实现四个示例OC；
- 写死NOV、PN当前计划数量；
- 为避免单支无人OC过期而制造被迫拆队风险；
- 用25%、50%、100%机械缩放代替三模式业务语义；
- 在缺少业务证据时声称某个停转方案收益最优；
- 在前置业务答卷和详细方案未确认前开始实施。
