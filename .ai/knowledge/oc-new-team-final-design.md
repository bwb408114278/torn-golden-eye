# OC新队重写——最终实现设计

> 状态：待用户确认后实施。本文档只定义实现，不代表已修改代码。

## 1. 目标与边界

### 1.1 目标

将 `OC新队` 从静态统计命令改为可执行的管理决策工具：

1. 读取当前 OC、固定在队成员、个人准备进度、空位和未来释放时间；
2. 计算现有空位如何补人；
3. 判断现有空 OC 中哪些值得启动、哪些应保留等待、哪些不应投入人员；
4. 给出继续刷新多少次的建议；
5. 给出成员、固定岗位、加入顺序、建议加入时间、成功率和门槛；
6. 输出保守、均衡、收益三个条件分支，并推荐一个；
7. 自动求出高阶链当前最多可安全并行几条，不写死 PN 为 1 或 2；
8. 新 OC / 新链在数据和流程资料齐全后，通过配置启用，不修改规划代码。

### 1.2 明确不做

- 不调整旧队已有成员的岗位；
- 不把旧队成员移到其他队；
- 不自动执行加入、拆队、删除或刷新游戏操作；
- 不考虑 Scope 余额、respect、帮派留存比例；
- 不使用历史成功率直接惩罚当前阵容；
- 不继续复用旧 `TornOcManageService` 的统计算法；
- 不让 `torn_setting_faction_oc_disable` 决定新队运行范围；该表继续服务成员 OC 推荐。

## 2. 已确认业务规则

1. 每名成员按加入顺序独立准备 24 小时；当前阶段剩余小时为：
   `24 × (1 - progress / 100)`，`progress` 范围 0～100。
2. 6 人队一次性全进占用 36 人天；逐阶段加入占用 21 人天。
3. 旧队已有成员、岗位和顺序均固定；只允许给空位补人。
4. 旧队优先不是等级优先，而是人员生产力解锁优先：低级旧队锁住高能力成员时仍可能优先救援。
5. 生成的根 OC 无数量上限；无人加入时 7 天过期；生成消耗 Scope 且不可回收；本版不对 Scope 建模。
6. 后继 OC 由前置成功产生，并需要新一批成员重新进入。
7. PN/CCRC/HP/SH 使用差异化工时系数；NOV/BSU 虽属大锅饭，但新队岗位评价方式与普通帮派相同。
8. 工时积分作为同等方案的岗位/顺序依据和解释，不压过全局可行性、生产力和收益目标。
9. 历史成功率受成员成长和流动影响，不用于运行时当前阵容预测。
10. 当前启用高阶链及未来 Lock Stock / Manifest Cruelty 链不得在算法中写死。

## 3. 核心建模

### 3.1 不可变规划快照

命令刷新 OC 后，一次性批量加载并构造 `OcPlanningSnapshot`：

- 当前时间；
- 帮派策略；
- 当前 Recruiting / Planning OC；
- 所有相关 Slot；
- 当前帮派成员及有效成功率矩阵；
- OC 模板、岗位门槛、帮派门槛覆盖；
- 工时系数；
- 启用的 OC 根范围和链图；
- 静态收益下界及历史直接净收益统计。

快照创建后求解期间不可变，避免刷新过程中数据漂移。

### 3.2 人员状态

`OcMemberState`：

- `userId / nickname`；
- `availableAt`：即时空闲或旧队预计释放时间；
- `fixedOcId / fixedSlotCode`：已有旧队占用，仅用于释放事件；
- `capabilities`：满足硬门槛的模板岗位集合；
- `scarcityScore`：可承担的稀缺岗位和替代人数；
- `incomeMode` 下的岗位工时系数（仅差异化工时帮派使用）。

旧队已有成员永不进入重新分配候选集。

### 3.3 OC状态

`OcInstanceState`：

- 根/后继；
- 当前状态、生成时间、过期时间；
- 固定成员和空位；
- 当前 `readyTime`；
- 当前阶段成员及 `progress`；
- 预计阶段结束时间；
- 完整队伍预计释放时间；
- 前置/后继关系；
- 是否在该帮派新队运行范围内。

### 3.4 事件

只在离散业务事件上推进时间：

- `MEMBER_AVAILABLE`：旧队完成后成员释放；
- `STAGE_COMPLETE`：当前成员 24 小时阶段完成；
- `SLOT_JOIN_DUE`：下一名成员应加入；
- `OC_EXPIRE`：空/未完成 OC 到期；
- `CHAIN_CHILD_AVAILABLE`：前置成功后条件性生成后继；
- `REPLAN_REQUIRED`：用户完成建议操作或刷新后重新运行命令。

不按每小时建立完整时间网格。

## 4. 高阶链安全容量

### 4.1 不是固定配额

不配置 `PN最多2条Stacking链`。规划器每次根据最新能力矩阵计算三个不同概念：

- `committedChainCount`：已经有人进入、必须承担后续责任的链；
- `startableAdditionalChainCountNow`：以当前已生成根 OC（或“现在刚生成一支根 OC”的假设）为起点，在7天有效期内还能安全启动几条；
- `absoluteSafeConcurrentChainCount`：两者之和，即当前快照下可证明安全的并行在制链上限。

该定义必须绑定“现在可启动且根节点7天过期”的有限窗口；不能把未来串行复用同一批人的无限产量误算成并行容量。

计算输入包括：

- 当前已承诺链及其所在节点；
- 可启动但尚未启动的根链 OC；
- 每条链全部成功后的后继人员需求；
- 与普通 7/8 OC 及旧队救援共享的稀缺岗位资源；
- 每个节点的7天过期约束；
- 当前和未来已知的成员释放事件。

人员成长后，安全容量自然从 2 增长到 3、4……。

### 4.2 强鲁棒安全约束

对于候选新增链数 `k`，构造“所有已承诺和拟启动前置均成功，因此所有后继责任都真实发生”的最坏结果场景。开始时间由求解器安排，可以主动错峰；不能为了简单而强行假设所有后继同一时刻出现，也不能通过无限延后绕过节点7天过期。

每个后继节点都视为一支全新的 OC，重新建立人员—岗位分配；前置队成员完成释放后可以作为普通候选重新参与，但绝不默认原队自动继承到后继，也不能在时间重叠时复用。

只有存在完整的时间扩展可行计划时，`k` 才安全：

1. 所有已经启动/有进度的旧队可继续推进；
2. 每条链的当前节点可完整配队；
3. 每条链成功后，链图上的每个后继节点都能在各自过期前获得完整阵容；
4. 同一成员的所有占用时间区间互不重叠；
5. 不依赖“未来也许会出现的新成员”或成员能力继续增长；
6. 不使用普通池安全储备、收益偏好等软条件人为降低绝对上限。

绝对安全并行数：

`absoluteSafeConcurrentChainCount = committedChainCount + max k where robustFeasible(k) = true`

实际建议启动数另行计算：

`recommendedAdditionalChainCount(mode) <= startableAdditionalChainCountNow`

- 保守模式保留更多关键岗位余量；
- 均衡模式保留合理的 7/8 级流水线能力；
- 收益模式可以更接近绝对安全上限；
- 这些都是方案选择，不得反过来篡改“当前最多几条一定可救活”的定义。

安全容量使用完整搜索/约束可行性验证而不是 Beam 近似；Beam 只用于已验证可行方案之间的软目标排序。若时间预算内只证明了下界而未证明 `k+1` 不可行，输出必须写成“已证明至少安全 N 条，上限尚未证明”，不得冒充最大值。人员成长后，同一套模型会自然得到更高的安全容量。

### 4.3 启动条件

一条新链不仅要证明当前根节点能配齐，还必须满足：

- 全链模板、岗位、门槛和关系均为 `READY`；
- 差异化工时帮派还必须具备完整工时系数，否则只允许观察、不纳入规划；
- 后继未知（如当前 Lock Stock）时，链状态为 `OBSERVE_ONLY`，绝不建议把新的空根节点作为正式链启动；
- 已经存在的 `OBSERVE_ONLY` 旧队仍进入快照：已有成员保持固定并贡献未来释放事件，但空位只显示“人工观察处理”，不由自动求解器补人；
- `absoluteSafeConcurrentChainCount > committedChainCount`；
- 本次方案的 `recommendedAdditionalChainCount(mode)` 允许增加链数。

这避免“根节点能开、后继出来后无解，只能人工拆队”。

## 5. 配置驱动扩展

### 5.1 不在算法中写 OC 名称

新增配置模型：

#### `torn_setting_oc_plan_profile`

- `oc_name + rank`；
- `spawn_pool`：根 OC 属于哪个生成按钮/池；
- `plan_status`：`DISABLED / OBSERVE_ONLY / READY`；
- `reward_floor`：可确认的直接净收益下界；
- `min_sample_size`：动态收益可用的最低样本数；
- `deleted / timestamps`。

#### `torn_setting_oc_chain`

- `chain_code`；
- `parent_oc_name / parent_rank`；
- `child_oc_name / child_rank`；
- `sequence_no`；
- `enabled / timestamps`。

#### `torn_setting_faction_oc_plan`

- `faction_id`；
- `oc_name / rank`；
- `enabled`；
- 可选 `reserve_ratio` 或其他帮派策略覆盖；
- `timestamps`。

#### 帮派策略

在帮派配置或独立策略表表达：

- `planning_mode`：`DIFFERENTIAL_WORK_HOUR / POSITION_WEIGHT`；
- 默认根生成池；
- 普通池安全储备比例；
- Beam 宽度等非业务执行参数使用应用配置而非表。

### 5.2 启用新链的完整性门禁

`OcPlanCatalogValidator` 在缓存预热和命令执行前检查：

- 模板存在；
- `required_members / prepare_days` 合法；
- 岗位数量与模板人数一致；
- 每个岗位门槛存在；
- 链图无环且父子唯一合法；
- `reward_floor` 存在；
- 差异化工时模式下每个岗位具备完整成功率区间系数；
- `READY` 节点的所有后继资料完整。

不完整时降级为 `OBSERVE_ONLY` 并在输出中说明缺失项，绝不让求解器默默按0处理。

## 6. 收益与风险模型

### 6.1 直接净收益

`cash + reward item value - consumed item cost`

不计 respect、Scope、帮派留存。

### 6.2 `expected_reward` 处理

当前字段没有业务引用。实施时不复用含糊语义：

- 优先新增/迁移为 `reward_floor`；
- 它只代表直接净收益保守下界；
- 链价值永不写入模板静态字段；
- 历史期望收益运行时从已完成记录批量聚合，样本不足时向 `reward_floor` 收缩。

### 6.3 链价值

规划分支显示条件性价值：

`parent direct value + child value if parent succeeds`

但由于当前阵容成功概率无法从岗位成功率可靠推导，运行时排序采用：

1. 全岗位硬门槛；
2. 收益等级/`reward_floor`；
3. 直接历史净收益（仅样本充足时）；
4. 最小岗位安全余量；
5. 链成功后的条件收益。

不把历史帮派成功率乘入当前阵容收益。

### 6.4 历史成功率用途

只用于：

- 离线配置校准；
- 观察某帮派/OC长期退化；
- 提醒门槛可能过低；
- 测试数据回放；
- 不进入单次计划目标函数。

当前阵容风险由岗位硬门槛、安全余量和候选替代性表达。

## 7. 求解架构

### 7.1 第一阶段：确定性可行性

`ExistingTeamRescuePlanner`：

- 固定旧队成员；
- 计算每个旧队下一空位的最晚加入时间；
- 用未来释放成员补空位；
- 评估新增一人可以解锁多少被占用生产力；
- 无完整未来可行路径的旧队不继续投入新成员，并标记人工处理风险。

### 7.2 第二阶段：新队/链可行阵容

`OcRosterMatcher` 使用最小费用最大流或等价精确匹配：

硬约束：

- 一人同一时段只属于一个 OC；
- 岗位门槛达标；
- 每个队伍必须存在完整完工路径；
- 固定旧队成员不可变；
- 过期前完成必要加入；
- 链鲁棒预留。

匹配成本：

- 人员等待；
- 稀缺成员机会成本；
- 高能力成员用在低可替代价值岗位的浪费；
- 过早加入产生的额外占用人天；
- 同等方案下的工时/岗位权重适配。

### 7.3 第三阶段：事件驱动 Beam Search

状态动作：

- 补旧队下一空位；
- 启动一个根 OC；
- 安排下一名成员在某事件点加入；
- 保留空 OC；
- 建议继续刷新一次；
- 停止刷新并等待释放事件。

每层只保留非支配状态及有限 Beam：

- 可完成队伍/链；
- 净收益等级；
- 占用成员人天；
- 空闲等待；
- 稀缺人员储备；
- 过期风险；
- 鲁棒安全容量。

### 7.4 三个输出方案

从 Pareto 前沿选取：

1. **保守**：最大化可救援旧队和鲁棒余量，最小化失败后人工拆队风险；
2. **均衡（默认）**：单位成员人天价值、旧队释放、普通池与高阶链之间的拐点；
3. **收益**：在所有硬约束和鲁棒链约束满足后，最大化长期条件净收益。

工时只作为同等方案的次级评价和解释。

## 8. 刷新策略

输出不是预测随机结果，而是条件策略：

- 当前立即使用哪个生成按钮、建议先刷新几次；
- 每刷新一次后要求重新运行命令；
- 如果刷到某个 OC，使用哪个分支；
- 如果刷到 `OBSERVE_ONLY` 或无完整阵容的 OC，不投入成员；
- 什么时候停止刷新并等待人员释放；
- 当前高阶 `absoluteSafeConcurrentChainCount / recommendedAdditionalChainCount / committedChainCount`。

为避免一次性刷新过多造成无法消化的空 OC，第一版建议采用单步滚动：

`建议刷新1次 → 获取真实随机结果 → 重新规划`

只有当多个可能结果都具有安全可行阵容时，才允许建议批量刷新多次。

## 10. DAO与查询

新增批量查询，不按 OC/成员循环：

1. 当前帮派 Recruiting/Planning OC；
2. 对应全部 Slot；
3. 当前帮派成员；
4. 相关模板/岗位的所有成员成功率；
5. 全局与帮派岗位门槛；
6. 工时系数；
7. 规划范围和链图；
8. 批量昵称；
9. 历史直接净收益聚合。

规划器接收聚合后的不可变 Map/List，禁止在搜索循环中访问数据库。

按真实 SQL 使用情况评估并通过 Liquibase 添加必要组合索引，例如：

- 当前 OC：`(faction_id, status, deleted, ready_time)`；
- Slot：`(oc_id, deleted, user_id)`；
- 能力矩阵：`(faction_id, rank, oc_name, position, user_id, deleted)`；
- 规划配置：唯一键和查询组合索引。

实际提交前必须 EXPLAIN 验证，不盲目加索引。

## 11. 并发与降级

- 单实例：使用 `ConcurrentHashMap<Long, ReentrantLock>` 做帮派级防重入；
- 仅锁“刷新 + 快照加载”，求解可基于快照进行；同帮派重复请求返回“规划中”或复用短期结果；
- 设置求解时间预算；超时返回当前最佳可行方案，并标注非最优；
- 配置不完整时禁止相关 OC，而非使用0门槛/0工时；
- 无任何完整方案时明确输出阻塞岗位和候选缺口，不伪造建议。

## 12. 测试矩阵

### 12.1 准备流水线

- 4/5/6人 OC 的占用人天分别验证为10/15/21；
- 一次性全员与逐阶段加入对比；
- progress=0、50、100 的阶段结束时间；
- 旧队成员固定且不可出现在新队候选中。

### 12.2 旧队救援

- 低级旧队锁住高阶稀缺成员时优先补齐；
- 缺口未来不可补齐时禁止继续投入；
- 多旧队争夺同一成员时全局选择而非逐队贪心；
- 补人时间恰好落在下一阶段前。

### 12.3 链安全容量

- 能力仅支持2条时返回2；
- 人员成长后自动返回3，无代码变化；
- 根能开但后继无完整阵容时容量不增加；
- 所有拟启动前置最终成功、全部后继责任均发生时的完整时间扩展场景；
- 普通池储备导致容量下降；
- 未知后继/缺系数链为 `OBSERVE_ONLY`。

### 12.4 帮派模式

- PN/CCRC/HP/SH 使用差异化工时；
- NOV/BSU和普通帮派使用岗位权重；
- 工时只打破同等方案，不覆盖硬约束和全局价值；
- 帮派自定义门槛生效。

### 12.5 收益

- 现金、物品、消耗品净值；
- 样本充足使用收缩历史均值；
- 新 OC 使用 `reward_floor`；
- 前置直接收益为负但链仍有价值；
- 历史成功率不影响当前计划排序。

### 12.6 输出与随机刷新

- 三方案可执行且差异明确；
- 推荐模式自动选择；
- 每个条件分支说明成员/岗位/时间/门槛；
- 单步刷新后要求重规划；
- 空 OC 7天过期风险展示。

## 13. 实施顺序（确认后）

1. 先补纯模型和求解器测试夹具；
2. Liquibase 增加规划配置、链关系和收益下界；
3. Catalog Manager + 完整性校验；
4. 批量快照加载与查询计划验证；
5. 旧队救援和时间线模拟；
6. 精确阵容匹配；
7. 安全链容量求解；
8. Beam Search + Pareto 选择；
9. 收益估算和工时次级排序；
10. 命令入口与输出；
11. 删除旧统计服务/BO；
12. 全量单元测试、JDK21 编译验证、代码审查。

## 14. 验收标准

- 对当前生产快照，输出可执行的成员、岗位、顺序和时间，而非统计；
- 不修改任何旧队已有成员；
- 每个推荐队伍都有直至完成的可行路径；
- 每条新高阶链都通过全链全成功结果下的时间扩展安全验证；
- 人员能力提高后，安全链数自动提高；
- 新链资料不完整时不可误启用；资料补齐并改为 READY 后无需修改规划代码；
- 无 N+1；
- 求解超时仍返回已验证可行方案；
- 历史成功率不作为当前阵容概率；
- 旧失败实现被干净删除。
